# 3. Embedding 与向量数据库

> 这一篇要回答的是：**"文本 → 向量"这一步到底做了什么，为什么它能让计算机"按语义"检索？**
>
> 主线一句话：
>
> ```
> 把「意思像不像」翻译成「几何上近不近」
> ```
>
> 这句话里藏着 RAG 最大的一个"魔术"，也藏着最大的三个坑。本文会把这些坑全部用真实数字挖出来：
>
> 1. **余弦、欧氏、内积**三种度量，在什么条件下等价、什么条件下互相打架（第 2、3 节，有推导）
> 2. Chroma 返回的那个 **`score` 到底是什么**——网上 90% 的教程在这里写反了（第 4 节，实测钉死）
> 3. 模型的 **512 token 硬上限**会让长文档被**静默截断**（第 5 节，有对照实验）
>
> 本文数字来自 `3_embedding.py` 的实跑输出，以及一组用真实向量做的实测（脚本已删除，均可复现）。

## 0. 先看真实运行

```
1. Embedding基础
============================================================
向量维度: 512
Python vs Java: 0.8931
Python vs 天气: 0.2460

2. Chroma向量数据库
============================================================
Chroma检索:
  [python.md] Python的装饰器用@符号应用
  [web.md] FastAPI是现代Web框架

带分数检索:
  分数: 0.5213 | PyTorch用于深度学习
  分数: 0.8744 | FastAPI是现代Web框架
```

先看第 1 段，这就是全部的魔术：

```
"Python是编程语言" ──→ 一个 512 维向量 ──┐
"Java是编程语言"   ──→ 一个 512 维向量 ──┤ 夹角 26.7°，余弦 0.8931  → 很接近
"今天天气很好"     ──→ 一个 512 维向量 ──┘ 夹角 75.8°，余弦 0.2460  → 离得远
```

（26.7° 和 75.8° 是反算出来的：`arccos(0.8931) = 26.7°`，`arccos(0.2460) = 75.8°`。）

**"意思像"被编码成了"方向接近"。** 机器不懂"编程语言"是什么，但它现在可以做一件事了：算夹角。

再看第 2 段的最后两行，这里有个**必须立刻警觉**的信号：

```
查询是「深度学习框架」
  分数: 0.5213 | PyTorch用于深度学习      ← 排第 1，分数更小
  分数: 0.8744 | FastAPI是现代Web框架     ← 排第 2，分数更大
```

PyTorch（深度学习框架）是正确答案，它的**分数更小**。如果这个 `score` 是"相似度"，正确答案的相似度怎么会更低？

**结论：这个 `score` 不是相似度，是距离。** 第 4 节会把它的公式推出来并用真实数据验证到小数点后四位。

## 1. Embedding 到底做了什么

### 它是从"语义空间"到"几何空间"的一次映射

```
   语义世界                              几何世界（512 维）
┌──────────────┐                    ┌──────────────────────┐
│ "Python是编程 │                    │ 向量 A [0.12, -0.34…]│
│  语言"        │ ──── 模型 f ───→   │                      │
│ "Java是编程   │                    │ 向量 B [0.11, -0.33…]│  A 和 B 方向接近
│  语言"        │                    │                      │
│ "今天天气很好"│                    │ 向量 C [0.78, 0.21… ]│  离 A、B 都远
└──────────────┘                    └──────────────────────┘
```

这个映射函数 `f` 就是 Embedding 模型。它有两条必须成立的**核心假设**：

| 假设 | 含义 | 不成立会怎样 |
|---|---|---|
| **语义相近 → 向量相近** | "Python 是编程语言"和"Java 是编程语言"挨在一起 | 检索就是瞎找 |
| **语义无关 → 向量远离** | "今天天气很好"不会挤到编程语言旁边 | 检索结果全是噪声 |

模型是通过对比学习训练出来的：训练时不断把"意思相近的句子对"拉近、把"无关的句子对"推远。它学到的是**共现模式**——经常出现在相同上下文里的词，方向就被拉近。

> 注意：模型学到的"相近"是**用法上的相近**，不是逻辑上的相近。所以"高"和"矮"会靠得很近（总是一起出现），"Python"和"蛇"也可能有一定相似度。这是后面所有"检索看起来很奇怪"的根源。

### 向量长什么样

`3_embedding.py` 用 `bge-small-zh-v1.5`，输出 **512 维**。第一句话的前 6 个分量实测是：

```
[-0.0062, 0.0013, 0.0552, -0.0079, -0.0147, 0.0172, ...]   ← 共 512 个
```

单看数字没有意义，**有意义的是距离**。这就是为什么全文不讨论"某个分量是什么"，只讨论"两个向量的夹角"。

### 维度意味着什么

| 模型 | 维度 | 说明 |
|---|---|---|
| `BAAI/bge-small-zh-v1.5`（本文用的） | **512** | 本地跑，约 100MB，CPU 上毫秒级 |
| `BAAI/bge-large-zh-v1.5` | 1024 | 中文效果更好，体积和耗时约 3 倍 |
| OpenAI `text-embedding-3-small` | 1536 | 需 API，每次调用花钱 |
| OpenAI `text-embedding-3-large` | 3072 | 效果最好，成本最高 |

维度不是越高越好。维度 ↑ → 表达能力强 ↑，但**存储 ↑、算距离耗时 ↑、小数据集上过拟合风险 ↑**。这套教程用的 `bge-small-zh` 只有 512 维，在下面第 7 节你会看到它带来的真实局限。

## 2. 三种相似度度量：数学上它们是一回事

这是本篇的核心推导。搞懂这一段，你就能看懂任何向量数据库返回的分数。

### 定义

设查询向量 `q`、文档向量 `d`，都是 n 维（本文 n=512）。

**余弦相似度**：只看夹角，不看长度

```
cos(q, d) = (q · d) / (‖q‖ · ‖d‖)


其中 q · d = Σᵢ qᵢdᵢ           （点积）
     ‖q‖   = √(Σᵢ qᵢ²)        （L2 模长）
```

**欧氏距离**：直线距离

```
L2(q, d) = ‖q − d‖ = √(Σᵢ (qᵢ − dᵢ)²)
```

**内积**：直接点积，不做归一化

```
IP(q, d) = q · d
```

### 关键推导：单位向量时，三者完全等价

**先假设 `q` 和 `d` 都是单位向量**（即 `‖q‖ = ‖d‖ = 1`，后面第 3 节会说明怎么保证这一点）。

把欧氏距离平方展开：

```
‖q − d‖² = (q − d) · (q − d)
         = q·q − 2(q·d) + d·d
         = ‖q‖² + ‖d‖² − 2(q·d)
         = 1 + 1 − 2cos(q,d)          ← 因为 ‖q‖=‖d‖=1，且 q·d = cos
         = 2 − 2·cos(q,d)
```

得到本篇最重要的一个公式：

```
┌────────────────────────────────────┐
│   L2²(q, d) = 2 − 2·cos(q, d)      │
└────────────────────────────────────┘
```

**它说明三件事：**

1. **`L2²` 和 `cos` 是一一对应的**。`cos` 越大（越相关）→ `L2²` 越小。所以"用欧氏距离排序"和"用余弦排序"**结果完全一样**。
2. `cos = 1`（完全同向）时 `L2² = 0`（重合）；`cos = 0`（正交）时 `L2² = 2`；`cos = −1`（反向）时 `L2² = 4`。所以 **`L2²` 的取值范围是 [0, 4]**。
3. 既然单位向量下 `q·d` 就等于 `cos`，那么**内积也和它们等价**。

### 实测验证：三种度量逐行吻合

用真实向量（`bge-small-zh-v1.5`，查询 `深度学习框架`）算出来：

| 文档 | `cos` | `L2²` | `1 − cos` |
|---|---|---|---|
| PyTorch用于深度学习 | 0.7393 | **0.5213** | 0.2607 |
| FastAPI是现代Web框架 | 0.5628 | **0.8744** | 0.4372 |
| Python的装饰器用@符号应用 | 0.4036 | 1.1929 | 0.5964 |
| GIL限制了多线程并行 | 0.3463 | 1.3074 | 0.6537 |

拿第一行手算核对：

```
cos = 0.7393
L2² = 2 − 2×0.7393 = 2 − 1.4786 = 0.5214     ← 表里是 0.5213，差在四舍五入 ✓
```

而 `0.5213` 正是第 0 节里 Chroma 返回的**第一个分数**。这就确认了 Chroma 默认用的是 `L2²`。

> **必须记住的前提**：上面这个等价关系**只在单位向量下成立**。一旦向量长度不一样，三者就分家了——这正是下一节的内容。

## 3. 为什么必须先归一化（真实验证）

如果向量不是单位长度，`L2²` 和 `cos` 的等价关系立刻崩掉。我用同一批真实向量做了一个对照：取两条语义相近的文本，把其中一条的向量**人为放大 2 倍**（语义完全没变，只是长度变了）。

| 度量的对象 | `cos(q, ·)` | `L2²(q, ·)` | `q · ·`（内积） |
|---|---|---|---|
| 文档 a（正常长度 1.0） | 0.5151 | 0.9697 | — |
| 文档 b（正常长度 1.0） | 0.5204 | 0.9591 | 0.5204 |
| **文档 b × 2**（长度 2.0） | **0.5204** ← 不变 ✓ | **2.9182** ← 翻了 3 倍 ✗ | **1.0409** ← 翻了 2 倍 ✗ |

**这是决定性的一组数字：**

- **余弦完全不受长度影响**（0.5204 → 0.5204）。因为它分母上就除了 `‖q‖·‖d‖`，长度被约掉了。
- **`L2²` 被长度严重污染**（0.9591 → 2.9182）。文档 b 和 b×2 **语义一模一样**，但 `L2²` 差了 3 倍。如果用它排序，一条"说了 3 遍同样内容"的长文档会被判为"很远"。
- **内积同样被污染**（0.5204 → 1.0409）。所以 `hnsw:space="ip"` 只在向量已归一化时才安全。

**结论：只要用 `l2` 或 `ip` 度量，就必须先把向量归一化。** 这不是可选项。

### 一个诚实的补充：对本模型来说，归一化参数是"空转"的

代码里写了：

```python
HuggingFaceEmbeddings(
    model_name=EMBEDDING_MODEL,
    encode_kwargs={"normalize_embeddings": True},
)
```

我在实测中对比了 `normalize_embeddings` 设 `True` 和 `False` 的输出，结果**完全一样**，两次的向量模长都是 **1.0000**：

```
normalize=True   |v| = 1.0   |q| = 1.0
normalize=False  |v| = 1.0   |q| = 1.0     ← 设 False 也是 1.0
```

原因是 `bge` 系列的 sentence-transformers 配置文件里**已经内置了一个 Normalize 模块**，模型输出天然就是单位向量。所以这个参数对 bge 是冗余的。

**为什么我还留着它？** 因为这是**防呆设计**：换成别的模型（比如某些不加归一化层的模型）时，这一行会立刻生效。显式写出来远比依赖"这个模型碰巧自带归一化"更安全。

> 这一条也是"读文档看不出来"的典型：参数看似在起作用，实际是空转。**只有实测才能发现。**

## 4. Chroma 的 `score` 到底是什么（实测钉死）

现在可以精确回答第 0 节留的问题了。Chroma 建 collection 时可以指定 `hnsw:space`，默认是 `l2`。我用同一批向量、同一个查询，在三种空间下各跑一遍，和 NumPy 手算的结果并排：

**空间 1：`l2`（默认）——返回平方欧氏距离 `2 − 2cos`**

| 文档 | NumPy 手算 `2−2cos` | Chroma 返回 `score` |
|---|---|---|
| 装饰器 | 0.9975 | **0.9975** ✓ |
| 生成器 | 1.2654 | **1.2654** ✓ |
| multiprocessing | 1.3669 | **1.3669** ✓ |
| GIL | 1.3975 | **1.3975** ✓ |
| 多线程 IO | 1.4532 | **1.4532** ✓ |
| asyncio | 1.6284 | **1.6284** ✓ |

**六行全部精确吻合到小数点后四位。**

**空间 2：`cosine`——返回 `1 − cos`**

| 文档 | NumPy 手算 `1−cos` | Chroma 返回 `score` |
|---|---|---|
| 装饰器 | 0.4988 | **0.4988** ✓ |
| 生成器 | 0.6327 | **0.6327** ✓ |
| multiprocessing | 0.6834 | **0.6834** ✓ |
| GIL | 0.6987 | **0.6987** ✓ |

**同样逐行吻合。**

**空间 3：`ip`——返回负内积**（本模型向量已是单位长度，所以等价于 `−cos`）

### 把结论固化成一张表

| `hnsw:space` | 返回的 `score` 含义 | 取值范围 | 越大越相关？ |
|---|---|---|---|
| `l2`（Chroma 默认） | `2 − 2·cos` | [0, 4] | **❌ 越小越相关** |
| `cosine` | `1 − cos` | [0, 2] | **❌ 越小越相关** |
| `ip` | `−cos` | [−1, 1] | ✅ 越大越相关 |

```
┌──────────────────────────────────────────────────────────┐
│  similarity_search_with_score 返回的是「距离」不是「相似度」│
│  → 不管用哪个空间（除 ip），都是【越小越相关】              │
└──────────────────────────────────────────────────────────┘
```

### 这直接推翻了一段流传很广的错误写法

网上（包括本教程的旧版）常见这样的"阈值过滤"：

```python
# ❌ 错的
filtered = [(doc, score) for doc, score in results if score > 0.7]
```

在 Chroma 默认的 `l2` 空间下，`score > 0.7` 筛出来的是**最不相关**的那批文档，而把最相关的（`score` 接近 0）全部扔掉。方向完全反了。

同一个仓库里的 `4_retrieval.py` 写的是对的（`score < 0.5`），而旧的 `4_retrieval.md` 写的是 `score > 0.7`——**文档和代码自相矛盾**，这处错误已经在第 4 篇修正。

> 但请注意：**改成 `<` 也只是把方向改对了，`0.5` 这个具体数值仍然不可靠。** 第 4 节数据里，6 条文档的 `score` 全部落在 `[0.9975, 1.6284]`，没有一条小于 0.5——照这个阈值过滤，会把**全部结果**丢掉。第 4 篇会专门讨论"阈值到底该怎么定"。

## 5. Embedding 模型的硬约束：512 token 上限

这是本篇第二个"不看源码发现不了"的坑。

`sentence-transformers` 加载模型时会读到一个 `max_seq_length` 配置。实测 `bge-small-zh-v1.5` 的值是：

```
max_seq_length = 512
```

**超过 512 token 的部分会怎样？** 我做了三组对照实验来确认（同一段文本的头 + 一段完全无关的尾巴）：

| 实验 | 构造 | token 数 | `cos(与实验 A 的向量)` |
|---|---|---|---|
| A | 头（GIL 相关内容 × 60 遍） | 1682 | 1.0（自身） |
| B | 头 + 尾巴（天气内容 × 60 遍） | 3422 | **1.000000** |
| C | 尾巴 + 头（顺序颠倒） | 3422 | **0.314223** |

A 和 B 的前 512 个 token **完全相同**（已验证），而 B 的总长度是 A 的两倍多。结果：

```
cos(encode(A), encode(B)) = 1.000000      ← 一模一样！
cos(encode(A), encode(C)) = 0.314223      ← 换了个顺序就完全不同
```

**A 和 B 的向量完全相同，精确到小数点后六位。**

也就是说：**B 里那 2910 个 token 的"天气"内容，对最终向量没有产生任何影响——它们被静默丢弃了。** 只有 512 token 参与计算。

### 为什么这件事非常危险

因为它**不报错**。你在日志里只会看到一条 tokenizer 的 warning：

```
Token indices sequence length is longer than the specified maximum sequence length
for this model (1682 > 512). Running this sequence through the model will result in
indexing errors
```

这条 warning 极易被忽略（跟第 2 篇那个 `Created a chunk of size 53...` 是同一类问题）。后果是：

1. 文档后半段的信息**完全检索不到**——不是效果差，是**根本进入不了向量**。
2. 你以为检索"漏了"，会去调 `k`、调检索策略，**方向全错**。

### 和第 2 篇的数字对上了

第 2 篇实测过：**中文 500 字符 ≈ 557 token**。而这里 `chunk_size=500` 意味着：

```
chunk_size = 500（字符）
   → 中文约 557 token
   → 已经超过 bge-small 的 512 token 上限 ✗
   → 尾部约 45 token 被静默截断
```

**这就是为什么"切分"和"Embedding"必须一起考虑：**

| | 限制单位 | 本文模型的限额 | 对应字符数（中文） |
|---|---|---|---|
| 切分器 `chunk_size` | **字符** | 无硬限制 | — |
| Embedding 模型 | **token** | **512** | 约 460 字符 |
| LLM 上下文 | **token** | 视模型而定 | — |

正确的做法是**倒着算**：从 embedding 的 512 token 限额出发，留出安全余量（比如目标 300 token），再换算成字符数 —— 中文约 `300 × 1.1 ≈ 330` 字符。**用 `tiktoken` 实测校验，不要凭感觉设。**

## 6. 一个真实的反直觉现象：绝对相似度不可用

回到 `3_embedding.py` 第 2 段的检索结果。我把 4 条短文档对两个查询的**全部**相似度算出来（不只是 Top-2）：

**查询 `什么是装饰器`：**

| 文档 | `cos` | `score = 2−2cos` |
|---|---|---|
| Python的装饰器用@符号应用 | **0.5293** ← 正确答案，Top-1 | 0.9414 |
| GIL限制了多线程并行 | 0.2646 | 1.4708 |

等等——正确答案的 `cos` 只有 **0.5293**？一半多一点的相似度？

**查询 `深度学习框架`：**

| 文档 | `cos` | `score` |
|---|---|---|
| PyTorch用于深度学习 | **0.7393** ← Top-1 | 0.5213 |
| FastAPI是现代Web框架 | 0.5628 | 0.8744 |

这里正确答案的 `cos` 是 0.7393。

**同一个模型、同一批文档，两个查询的"正确命中"相似度分别是 0.5293 和 0.7393——差了 0.21。** 加上第 1 篇测到的"5 条文档全挤在 0.58~0.66 之间"，结论已经很清楚了：

```
┌────────────────────────────────────────────────────────────┐
│ 相似度的绝对值没有可比性。                                   │
│ 它只在【同一次查询的候选集内部】做相对排序时有意义。          │
│ 跨查询不可比、跨数据集不可比、跨模型更不可比。                 │
└────────────────────────────────────────────────────────────┘
```

**为什么？**

1. **不同查询的"语义密度"不同**。"深度学习框架"是个很集中的概念，容易找到高相似度的文档；"什么是装饰器"这种口语化问句，和陈述句文档的措辞差异大，天然相似度就低。
2. **语言模型的向量空间不是均匀的**。有些区域向量的角度天然分布得更开。所有 embedding 模型都有这种现象，不是这个模型坏了。
3. **小模型 + 短文本雪上加霜**（第 1 篇量化过：极差只有 0.0857）。

**所以第 4 篇要讲的事情有了明确的动机：既然单一阈值靠不住，就只能换思路——**

| 错误思路 | 正确思路 |
|---|---|
| 定一个绝对阈值，低于它就不要 | 固定取 Top-K，让 LLM 自己判断资料够不够 |
| 用相似度数值判断"够不够相关" | 用**相对排名**、或**多种召回方式投票**（混合检索） |
| 指望阈值跨场景通用 | 用**评估指标**（命中率/MRR）在**你自己的数据**上调参 |

## 7. 向量数据库与持久化

### 选型

| 数据库 | 部署 | 距离度量 | 适合什么 |
|---|---|---|---|
| **Chroma**（本文用） | 内嵌，零配置 | l2 / cosine / ip | 开发、学习、几万条以内的小项目 |
| FAISS | 内嵌 | l2 / ip | 纯本地、追求速度和规模，但不带元数据过滤 |
| Milvus | 独立服务 | 多种 | 百万级以上、生产环境 |
| Pinecone / Weaviate | 云托管 | 多种 | 不想运维 |

Chroma 的优势是**零配置**：`Chroma.from_documents(docs, embeddings)` 一行就建好了，默认跑在内存里。学习和开发阶段没必要上 Milvus。

### 持久化实测

`3_embedding.py` 第 3 节演示了两件事：

```
已保存到 ./chroma_db
从磁盘加载并检索: 测试文档
```

写盘：`Chroma.from_documents(docs, embeddings, persist_directory="./chroma_db")`
读取：`Chroma(persist_directory="./chroma_db", embedding_function=embeddings)`

**注意读取时必须传入同一个 `embedding_function`。** 数据库里存的是向量，查询时要靠它把问题编码到**同一个向量空间**。换模型 = 换坐标系，检索结果会完全错乱。

### ⚠️ 一个必须知道的坑：重复写入是"追加"不是"重建"

我实测了两种情况下重复调用 `Chroma.from_documents` 的后果：

**内存模式（同一进程内调用两次）：**

```
第一次后 count = 6
第二次后 count = 12      ← 翻倍了
```

**持久化模式（脚本跑两遍）：**

```
第一次运行后 count = 1
第二次运行后 count = 2   ← 又加了一条
```

**原因**：Chroma 的 collection 有一个名字，LangChain 的默认名字是 `"langchain"`。`from_documents` 的语义是"往这个 collection 里**写入**这些文档"，**不是**"清空后重建"。同名 collection 已存在时，文档就被追加进去了。

**后果**：检索结果里会出现**同一条文档的多份副本**，白白占掉 Top-K 的名额。

这个坑在本教程的 5、6、7 号脚本里**真实发生过，并且造成了错误结论**：

```
（修复前 6_rag_optimization.py 的真实输出）
原始检索: ['asyncio是Python的异步编程库…', 'asyncio是Python的异步编程库…']   ← 同一条！
HyDE检索: ['asyncio是Python的异步编程库…', 'asyncio是Python的异步编程库…']
合并去重: 6 → 1 个文档                                                     ← 3 路召回全撞车
```

`5_rag_chain.py` 和 `6_rag_optimization.py` 都已经修复（做法见第 5 篇的说明）。**7 号脚本的索引模式仍有这个特性**——重复执行 `--mode index` 会让索引不断膨胀，第 7 篇会详细说明怎么规避。
