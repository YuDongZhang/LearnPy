# 2. 文档加载与切分

> 这一篇只回答一个问题：**为什么"文档 → 块"这一步决定了整个 RAG 系统的上限？**
>
> 主线只有一条：
>
> ```
> 原文（一大坨） → 切成块 → 【每块 = 一个向量 = 检索的最小单位】
> ```
>
> 关键在于第三个括号里的那句话。向量数据库里**不存在"半块"**，检索只能以块为单位返回。所以：
>
> - 块太大 → 一个向量要同时表示好几件事 → 语义被"平均"掉 → 检索不准
> - 块太小 → 一句话被劈成两半 → LLM 拿到残句 → 答不准
>
> 后面第 3、4 篇的检索效果好坏，**在这里就已经被锁死了**。切分是上游，检索是下游，上游切坏了下游救不回来。
>
> 本文所有数字都来自 `2_document_loading.py` 的实跑输出，以及一组配套的实测实验（脚本已删除，但每个数字都可复现）；凡是与代码输出不一致的地方，文中会明确标出。

---

## 0. 先看要处理的原料

代码第 2 节用了一段 206 字符的中文文本，它是标准的"三段式"中文文档：**4 个自然段，段落之间用空行分隔，段内用"。"分句**。

```
原文 206 字符 / 168 token
┌──────────────────────────────────────────────┐
│ 段1  Python是一种广泛使用的高级编程语言。它由  │
│      Guido van Rossum于1991年创建。          │
│                    ← 空行（\n\n）             │
│ 段2  Python的设计哲学强调代码的可读性和简洁性… │
│                    ← 空行（\n\n）             │
│ 段3  Python拥有丰富的标准库和第三方库生态系统… │
│                    ← 空行（\n\n）             │
│ 段4  Python的GIL（全局解释器锁）是CPython…    │
└──────────────────────────────────────────────┘
```

**先记住这三个数**：`206 字符`、`168 token`、`4 段`。后面每一节都在解释"切分器对着这 206 个字符做了什么决定"。

> **为什么上来就要算 token？** 因为**向量模型和 LLM 的限额都是按 token 算的，而 `chunk_size` 是按字符算的**。这两个单位之间的换算关系，是本篇最容易被忽略的坑（第 3 节）。

## 1. 加载：Loader 交给你的东西长什么样

代码第 1 节用 `TextLoader` 读一个 txt 文件，真实输出：

```
加载了 1 个文档
内容: Python是一种高级编程语言。

它由Guido van Rossum创建。

Python以简洁著称。
元数据: {'source': 'sample.txt'}
```

注意这一行输出里藏着 RAG 的最小数据单元 —— `Document` 对象只有**两个字段**：

| 字段 | 内容 | 在 RAG 里干什么 |
|---|---|---|
| `page_content` | 正文文本 | **会被转成向量**，用来做相似度检索 |
| `metadata` | `{'source': 'sample.txt'}` | **不转向量**，只在回答阶段用来标注"来源" |

这个分工非常重要，它解释了一件反直觉的事：**`metadata` 里的内容检索不到**。因为向量只由 `page_content` 算出来。如果你希望"按文件名检索"能生效，就必须把文件名拼进 `page_content`（第 8 节会给出这个技巧）。

常见 Loader 与依赖：

| 格式 | Loader | 额外依赖 |
|---|---|---|
| TXT | `TextLoader` | 无（**注意要传 `encoding="utf-8"`**，Windows 默认编码是 GBK，中文会乱码/报错） |
| PDF | `PyPDFLoader` | `pip install pypdf` |
| Word | `Docx2txtLoader` | `pip install docx2txt` |
| Markdown | `UnstructuredMarkdownLoader` | `pip install unstructured` |
| 网页 | `WebBaseLoader` | `pip install beautifulsoup4` |
| 整个目录 | `DirectoryLoader` | 用 `glob` 批量匹配（第 7 篇会用到） |

## 2. 为什么必须切分（三个硬理由，不是习惯问题）

### 理由一：模型有硬性输入上限

Embedding 模型不能吃无限长的文本。本文用的 `bge-small-zh-v1.5` 上限是 **512 token**（OpenAI 的 `text-embedding-3-small` 是 8191 token）。超出上限的部分**不会报错，会被静默截断**——后面的内容等于没写。第 3 篇有实测：构造两段"前 512 token 完全相同"的长文本，它们的余弦相似度**精确等于 1.000000**。这是物理约束，没得商量。

### 理由二：一个向量只能表示一个"平均语义"（核心）

这是切分真正的理由。向量模型把一整段文本压成**一个**固定维度的向量（本文用的 `bge-small-zh-v1.5` 是 512 维），这个过程本质上是**取平均**。

设想一块里同时写了三件事：GIL 的限制、装饰器的用法、FastAPI 的特点。这个块会得到什么向量？它得到的向量是这三件事的**混合体** —— 离"GIL"有点近，离"装饰器"也有点近，但**离哪个都不够近**。

```
块太大（一段一个向量）：
   "GIL限制…装饰器…FastAPI…"  →  [一个模糊的平均向量]  → 查什么都能匹配上一点，但都不精准

块适中（一件事一个向量）：
   "GIL限制多线程并行"        →  [一个锐利的向量]      → 查 GIL 时排第一
   "装饰器用@符号应用"        →  [另一个锐利的向量]     → 查装饰器时排第一
```

检索靠的是"距离排序"。混合向量会让所有查询的得分都被拉到中间，**排序就乱了**。所以切分不是为了省 token，是为了**让每个向量只表达一件事**。

### 理由三：上下文纯净度

第 4、5 篇会看到，检索结果是拼进 Prompt 交给 LLM 的。如果 Top-2 里有一块是无关内容，LLM 要么被干扰，要么把无关内容当成了依据 —— 这是幻觉的典型来源。**喂进去的每一块都在消耗 LLM 的注意力预算。**

## 3. 度量单位：`chunk_size` 是字符，但限制是 token

这一节是本篇第一个"光看文档看不出来"的坑。

`chunk_size=500` 是什么单位？**字符数**。而模型的限制是 **token 数**。中文和英文的字符/token 换算比差了 4 倍以上，实测：

| 文本 | 字符数 | token 数 | 字符/token |
|---|---|---|---|
| 中文（本文示例段落） | 234 | 209 | **1.12** |
| 英文（同类内容） | 243 | 58 | **4.19** |

再看"各取 500 字符"的对照（实测）：

```
中文 500 字符 → 557 token     ← 已经超过 500，token 比字符还多！
英文 500 字符 →  88 token
─────────────────────────────
同样 chunk_size=500，中文块是英文块的 6.3 倍 token 量
```

**两个直接结论**：

1. 网上教程说"`chunk_size` 常用 500~1000"，那是**英文语境**。中文文档按 1000 设，实际是 1000+ token 一块，可能已经顶到某些模型的上限。
2. 中文里 `chunk_size=500` 是个**相当大**的块（约 557 token），未必符合"小块精准检索"的初衷。

**所以正确的做法不是抄一个数字，而是倒着算**：

```
目标：一块 200~400 token（这是检索精度和上下文完整度的常见平衡点）
中文：chunk_size ≈ 目标token × 1.1
   → 想要 300 token，chunk_size 设 330 左右
英文：chunk_size ≈ 目标token × 4
   → 想要 300 token，chunk_size 设 1200 左右
```

用 `tiktoken` 实测校验（第 9 节给出代码）。

## 4. 递归切分器到底在做什么（本文核心）

`RecursiveCharacterTextSplitter` 是所有教程的默认推荐，但"递归"这两个字几乎没人讲清楚。**它不是递归函数，而是"分隔符优先级的逐级降级"。**

代码第 2 节传入了 `separators=["\n\n", "\n", "。", " ", ""]`，含义是：

```
第1级  "\n\n"  先尝试按"空行"切 → 得到自然段
第2级  "\n"    如果还有段落太长，退一步按"换行"切 → 得到行
第3级  "。"    再退一步按"中文句号"切 → 得到句子
第4级  " "     再退一步按"空格"切 → 得到词
第5级  ""      最后兜底：按"逐个字符"硬切
```

**每一级只处理上一级切完仍然超长的那些片段。** 用一段真实文本验证（234 字符的长段落，没有空行、没有空格）：

```
_merge_splits 收到 separator=''，6 个片段:
   片段1 (53字): Python的装饰器本质上是一个接受函数并返回函数的高阶函数…增强函数行为
   片段2 (44字): 。常见的应用场景包括记录日志、统计耗时、做缓存、检查权限…路由表中
   片段3 (37字): 。使用@语法糖时，装饰器会在函数定义时立即执行并把返回的新函数绑定到原名上
   片段4 (35字): 。如果装饰器需要接收参数，就要多写一层闭包，这是初学者最容易写错的地方
   片段5 (64字): 。functools.wraps的作用是把原函数的名称和文档字符串复制到包装函数上…函数名
   片段6 ( 1字): 。
```

因为文本里没有空行也没有空格，"`\n\n`"和"`\n`"这两级被跳过，实际生效的是"`。`"（所以片段长度是"句子"长度），末尾那个 1 字的片段是句号被当分隔符后的残留。

### 合并阶段：把碎片拼回 `chunk_size`

拿到这 6 个碎片后，切分器开始**贪心合并**：从前往后累加，加到再加就超 `chunk_size` 就吐出一块。`chunk_size=100`、`chunk_overlap=20` 的手算过程（源码在 `langchain_text_splitters.character` 的 `_merge_splits`）：

| 步骤 | 当前累计 | 判断 | 动作 |
|---|---|---|---|
| 放入 53 | 53 | 53 ≤ 100 | 继续 |
| 放入 44 | 53+44 = **97** | 97 ≤ 100 | 继续 |
| 放入 37 | 97+37 = 134 | **134 > 100** | 吐出第一块（97 字），回退重叠（见第 5 节） |
| 放入 37 | 37 | — | 作为新块的开头 |
| 放入 35 | 37+35 = **72** | 72 ≤ 100 | 继续 |
| 放入 64 | 72+64 = 136 | **136 > 100** | 吐出第二块（72 字） |
| 放入 64 | 64 | — | 新块开头 |
| 放入 1 | 64+1 = **65** | 65 ≤ 100 | 结束，吐出第三块（65 字） |

**手算结果 `[97, 72, 65]`，与实跑完全一致** ✓

```
实跑输出（chunk_size=100, overlap=20）：
   块1 (97字)  块2 (72字)  块3 (65字)
```

> **记住这个心智模型**：切分 = **先按优先级降级切碎，再贪心合并到接近 `chunk_size`**。
> 所以"块长度"几乎从来不会**正好**等于 `chunk_size`，它总是在片段边界上停下 —— 这是我们希望的，因为片段边界 = 语义边界。

## 5. `chunk_overlap` 的真相：它经常根本不生效

教科书的说法是"重叠防止上下文在块边界被切断"。**这句话是对的，但只在你把 overlap 设得足够大时才成立。**

实测同一段 234 字符的文本，`chunk_size=100`，逐步加大 `chunk_overlap`：

| `chunk_overlap` | 块数 | 各块长度 | 总字符 | 膨胀率 |
|---|---|---|---|---|
| 0 | 3 | [97, 72, 65] | 234 | 1.00x |
| 5 | 3 | [97, 72, 65] | 234 | 1.00x |
| 10 | 3 | [97, 72, 65] | 234 | 1.00x |
| 20 | 3 | [97, 72, 65] | 234 | 1.00x |
| 30 | 3 | [97, 72, 65] | 234 | 1.00x |
| **40** | 3 | [97, 72, 100] | 269 | 1.15x |
| **50** | 4 | [97, 81, 72, 100] | 350 | **1.50x** |

**`overlap` 从 0 加到 30，输出一个字符都没变。** 这不是 bug，是设计使然。

### 为什么会这样：回退是"整片段"级别的

看源码里吐出块之后的那段回退逻辑：

```python
while total > self._chunk_overlap or (...):
    total -= self._length_function(current_doc[0])   # ← 整片弹出，不是按字符截取
    current_doc = current_doc[1:]
```

它做的事是**从当前块的开头，把"整个片段"一个一个弹出去，直到剩余长度 ≤ `chunk_overlap`**。它不能"只弹半个片段"。

用片段 `[53, 44, 37, 35, 64, 1]` 手算三种 overlap：

**`overlap=20`**（吐出 97 字块，此时 `current_doc=[53,44]`，`total=97`）
```
97 > 20  → 弹掉 53 → total=44
44 > 20  → 弹掉 44 → total=0     ← 已经弹空了！
0  > 20? 否，循环结束
结果：current_doc=[]，新块从片段3(37)开始 → 完全没有重叠
```

**`overlap=40`**（同样的起点）
```
97 > 40  → 弹掉 53 → total=44
44 > 40  → 弹掉 44 → total=0     ← 还是弹空
结果：仍然没有重叠
```
但是后面第二处回退（吐出 72 字块时）情况变了：`total=72`
```
72 > 40  → 弹掉 37 → total=35
35 > 40? 否 → 循环结束       ← 这里留住了 35 字的片段4
结果：块3 = 片段4+5+6 = 35+64+1 = 100 字（而原来是 65 字）
```

**`overlap=50`**（第一处回退）
```
97 > 50  → 弹掉 53 → total=44
44 > 50? 否 → 循环结束       ← 留住了 44 字的片段2
结果：块2 = 片段2+3 = 44+37 = 81 字（原来是 72 字），块数从 3 变 4
```

三处手算结果 `[97,72,65]`、`[97,72,100]`、`[97,81,72,100]` **与实测表格逐行吻合** ✓

### 结论（这一节最该记住的）

1. **`chunk_overlap` 以"片段"为粒度生效。** 如果你设的 overlap 比最小片段还小，回退时会直接弹空 —— 等于**根本没设重叠**，但你仍然以为自己做了优化。
2. **重叠有真实代价。** `overlap=50` 时总字符 350 vs 原文 234，**膨胀 1.50x** —— 意味着 embedding 调用量和向量库体积都增加 50%。overlap 不是越大越好，它在花你的钱。
3. **必须实测验证，不能拍脑袋。** 第 9 节给出验证方法（打印相邻块的共享内容）。

> 顺便看代码第 2 节的输出：4 块长度 `[48, 51, 52, 49]`，加起来 **200 字符**，比原文 206 少了 6 个 —— 正好是 3 个 `\n\n` 分隔符（各 2 字符）。**分隔符本身不会进入块内容**，这也是切分的一个隐含损耗。

## 6. 中文必须自己传 `separators`（否则会切坏）

LangChain 的**默认** `separators` 是 `["\n\n", "\n", " ", ""]` —— 这是为**英文**设计的：英文靠空格分词，所以第 4 级用 `" "` 很合理。中文没有空格，第 4 级形同虚设，会一路掉到最后的"按字符硬切"。

实测对比（234 字符长段落，`chunk_size=100`）：

```
默认 separators ["\n\n","\n"," ",""]：
   3 块, 长度 [100, 100, 34]
   块1: …在前提下增强函数行为。常见的应      ← 结尾"常见的应"
   块2: 用场景包括记录日志…                  ← "用场景"被劈到下一块！

加 "。" 的 separators ["\n\n","\n","。"," ",""]：
   3 块, 长度 [97, 72, 65]
   块1: …增强函数行为。常见的应用场景…路由表中    ← 在句子边界结束
```

**"常见的应 | 用场景"** 这就是默认参数切中文的真实后果：一个词被劈成两半，两块各自表述了一个不完整的意思，语义被稀释。

> **但这里要诚实说明一个反例**：代码第 2 节的例子里，默认 separators 和中文 separators 的**输出完全相同**，都是 4 块 `[48, 51, 52, 49]`。原因很简单 —— 那段文本的**每个自然段都短于 `chunk_size=100`**，靠第 1 级 `"\n\n"` 就切完了，`"。"` 这一级**一次都没被用到**。
>
> 这是很重要的一课：**参数的影响取决于你数据的形态**。示例数据太"乖"，掩盖了参数差异。要发现问题，必须用真实数据（长段落、超长句）去压测。

## 7. 末尾那个 `""` 不能删（会静默切出超长块）

`separators` 列表最后一个 `""` 是**兜底**：当所有分隔符都切不动时，按单个字符硬切，保证任何情况下都不会超出 `chunk_size`。

删掉它会怎样？实测 `separators=["\n\n"]`、`chunk_size=30`：

```
4 块, 长度 [48, 53, 54, 51]      ← 全部超过 chunk_size=30，最长的超了 80%！
   块1 (48字): Python是一种广泛使用的高级编程语言。它由Guido van Rossum于1991年创建。
   块2 (53字): \nPython的设计哲学强调代码的可读性和简洁性…
```

`chunk_size=30` 却切出 53 字的块 —— **因为空行之间的段落有 48~54 字，而 `"\n\n"` 切不动段落内部，又没有任何更低级别的分隔符可以降级**。切分器只能原样保留，并且**只打一条 `logger.warning`，不抛异常**：

```
Created a chunk of size 53, which is longer than the specified 30
```

**这个警告极易被忽略，后果却很硬**：块长一旦超过 embedding 模型的 token 上限（本文用的 `bge-small-zh-v1.5` 是 512 token），超出部分会被**静默截断**——向量化照样成功、不报任何错，但超限的那部分内容等于从没存在过（第 3 篇实测过：两段"前 512 token 相同"的长文本，余弦相似度精确等于 1.000000）。结果就是库里多了一条"看起来完整、实际缺了一截"的文档，而且**你查不出来**。**兜底选项不是可选项。**

## 8. 按标题切分：把文档结构变成可检索的元数据

`MarkdownHeaderTextSplitter` 用完全不同的思路：**不按长度切，按标题层级切**。代码第 3 节实测输出：

```
Markdown切分: 5 块
  标题: {'h1': 'Python基础'} | 内容: Python是高级编程语言，语法简洁。
  标题: {'h1': 'Python基础', 'h2': '变量和类型'} | 内容: Python是动态类型语言…
  标题: {'h1': 'Python基础', 'h2': '函数'} | 内容: 使用def关键字定义函数。
  标题: {'h1': '高级特性', 'h2': '装饰器'} | 内容: 装饰器用于修改函数行为。
  标题: {'h1': '高级特性', 'h2': '生成器'} | 内容: 使用yield关键字创建生成器。
```

注意 `metadata` 是**逐级累积**的：`h2` 的块同时带着它的 `h1`。这个设计的价值有三个：

1. **可过滤检索**：`db.similarity_search(q, filter={"h1": "高级特性"})` —— 把搜索范围限定在某一大类里（第 4 篇会用到）。
2. **标题是极好的语义信号**：内容"装饰器用于修改函数行为"如果单独看，不知道说的是哪门语言的什么特性。把标题拼进正文（`"高级特性 > 装饰器：装饰器用于修改函数行为"`）能让向量更准确 —— 这正好补上了第 1 节说的"`metadata` 检索不到"的短板。
3. **切割天然对齐人的阅读结构**。

**但它有个必须知道的限制：`MarkdownHeaderTextSplitter` 完全不看 `chunk_size`。** 一个 `##` 章节如果有 5000 字，它就切出一个 5000 字的块。所以生产里的常见做法是**组合使用**：

```python
from langchain.text_splitter import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

# 第一层：按标题切出"章节"
md_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=[("#","h1"),("##","h2")])
sections = md_splitter.split_text(md_text)

# 第二层：把超长章节再用递归切分器打碎，metadata（h1/h2）自动继承
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=300, chunk_overlap=50, separators=["\n\n", "\n", "。", " ", ""]
)
chunks = text_splitter.split_documents(sections)
```

这样既拿到了结构化的 `metadata`，又保证了每块长度可控。**`split_documents` 会自动把原 `Document` 的 `metadata` 复制到每个子块**，实测确认：

```
原文档 metadata: {'source': 'decorator.md', 'page': 3}
拆成 3 块 → 块1/块2/块3 的 metadata 全部都是 {'source': 'decorator.md', 'page': 3}
```

## 9. 参数怎么定：一个可执行的流程

不要抄"500/1000/50"。按这个顺序做，每一步都有实测依据：

### 第 1 步：算出你数据里的字符/token 比

```python
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
text = open("your_doc.txt", encoding="utf-8").read()
print(f"{len(text)} 字符 = {len(enc.encode(text))} token")
print(f"字符/token = {len(text)/len(enc.encode(text)):.2f}")
```

本文示例（`cl100k_base` 编码）：中文得 **1.12**，英文得 **4.19**。差异极大，必须用**你自己的数据**测。

> **用什么 tokenizer？必须和你实际用的 embedding 模型一致**——因为"截断"就发生在它那里。上面用的是 OpenAI 的 `cl100k_base`；而本文第 7 篇用的是本地 `BAAI/bge-small-zh-v1.5`，换成它自己的 tokenizer（`AutoTokenizer.from_pretrained(EMBEDDING_MODEL)`）实测：`concurrency.txt` 397 字符 = **293 token**（1.36 字符/token）。**换 tokenizer，这个比值就会变**，所以要按你实际用的模型来量。

### 第 2 步：从目标 token 反推 `chunk_size`

```
chunk_size = 目标 token 数 × （字符/token）
目标 300 token、中文 → chunk_size ≈ 300 × 1.12 ≈ 336
目标 300 token、英文 → chunk_size ≈ 300 × 4.19 ≈ 1257
```

### 第 3 步：验证切分质量（三项检查）

```python
for i, c in enumerate(chunks):
    n = len(c.page_content)
    print(f"块{i+1}: {n} 字符, 结尾='{c.page_content[-10:]}'")
```

| 检查项 | 看什么 | 不达标说明 |
|---|---|---|
| 长度分布 | 是否都 ≤ `chunk_size` | 有超长的 → 检查 `separators` 末尾的 `""` 是否还在（第 7 节） |
| 结尾形态 | 是否停在句号/换行处 | 结尾是半个词（如"常见的应"）→ 需要补中文分隔符（第 6 节） |
| 相邻块重叠 | 打印块 i 结尾、块 i+1 开头，看是否真的有重复 | 完全无重复 → 你的 `overlap` 可能小于最小片段而**静默失效**（第 5 节） |

### 第 4 步：用重叠验证代码确认 overlap 真生效

```python
for i in range(len(chunks) - 1):
    a, b = chunks[i].page_content, chunks[i+1].page_content
    print(f"块{i+1}结尾: ...{a[-15:]}")
    print(f"块{i+2}开头: {b[:15]}...")
```

本文实测反例（`chunk_overlap=20`，但**没生效**）：

```
块1结尾15字: ...及注册函数到某个框架的路由表中
块2开头15字: 。使用@语法糖时，装饰器会在函...
                ↑ 不是重复，是全新的内容 → overlap 白设了
```

对比 `chunk_overlap=50`（**生效了**，块2 开头多了片段2 的 44 字）：

```
块2 = [片段2(44字)] + [片段3(37字)] = 81 字   ← 44 字是重叠进来的
```

## 10. 与后续章节的连接

这一篇的每个决定，都会在后面三篇里以具体形式显现：

```
本篇的决定                          →  后果出现在
───────────────────────────────────────────────────────────
chunk_size 太大（中文没换算 token）  →  第 3 篇：一个向量混合多主题，相似度全部趋同
separators 没加"。"                 →  第 4 篇：检索命中的块是半句话，看分数正常但内容没用
chunk_overlap 静默失效              →  第 5 篇：答案不完整（关键句被切在块边界外）
metadata 没保留 source/page         →  第 5 篇：无法标注来源，追溯功能直接失效
```

| 代码位置 | 在做什么 | 本篇得出的结论 |
|---|---|---|
| 第 1 节 `TextLoader("sample.txt", encoding="utf-8")` | 加载纯文本 | `encoding` 必须显式指定，否则 Windows 下中文报错 |
| 第 2 节 `chunk_size=100, chunk_overlap=20` | 递归切分 206 字符 → 4 块 | 块长落在片段边界上（`[48,51,52,49]`），不会正好等于 `chunk_size` |
| 第 2 节 `separators=[..., "。", " ", ""]` | 给中文补句号分隔符 | 本例中没生效（段落太短），长段落时才能看出差别 |
| 第 3 节 `MarkdownHeaderTextSplitter` | 按标题切 | 得到 `{'h1':…, 'h2':…}`，可过滤检索、可拼进正文 |
| — | — | `chunk_overlap` 的生效粒度是"片段"，必须实测验证 |
