# 1. RAG 概述与原理

> 这一篇只回答一个问题：**RAG 到底在解决什么问题，它的边界又在哪里？**
>
> 大部分教程把 RAG 讲成"检索 + 生成"，这只说清了**是什么**，没说清**为什么**。本文想讲明白的核心直觉是一句话：
>
> ```
> 把 LLM 从「闭卷考试」改成「开卷考试」
> ```
>
> 闭卷 = 只能靠参数里记住的东西答题；开卷 = 允许它先翻书，再拿着书上的原文作答。RAG 全部的价值与局限，都从这句话推得出来。
>
> 本文所有数字都来自 `1_rag_overview.py` 的实跑输出，以及一组用真实向量做的实测（脚本已删除，数字可复现）。凡是与代码输出不一致的地方，文中会明确标出。

---

## 0. 先看一次真实运行

代码只做五件事：准备 5 条文档 → 切分 → 向量化 → 检索 → 生成。真实输出：

```
文档数: 5 → 切分后: 5 块
向量数据库构建完成

查询: Python的GIL是什么？
检索到 2 个相关文档:
  [1] Python的装饰器是一种修改函数行为的语法糖，使用@符号应用。常用于日志、缓存、权限控制。...
  [2] Python的GIL（全局解释器锁）限制了多线程的并行执行。CPU密集型任务建议使用多进程。...

回答: Python的GIL（全局解释器锁）限制了多线程的并行执行。CPU密集型任务建议使用多进程。
```

请**盯着 [1] 那一行看十秒**。

用户问的是 GIL，检索结果的**第 1 名却是装饰器**。也就是说：

- 检索**排错了**（正确答案排在第 2）
- 但最终**回答是对的**

为什么答对了？因为 `k=2`，把第 2 名也一起捞进来了。如果这里写的是 `k=1`，LLM 拿到的上下文全是装饰器，它会**自信地**开始讲装饰器——这就是幻觉的生成方式：不是模型在瞎编，而是**你喂错了东西**。

这个案例包含了本文要讲的全部要点，后面逐层展开。

---

## 1. 为什么需要 RAG：LLM 的三个硬伤

### 硬伤一：知识被冻结在训练截止日期

模型的"知识"是训练时**压进参数**的。训练结束的那一刻，它的知识就定格了。今天发生的新闻、上周改的 API、昨天发布的版本，它一概不知。

这不是"模型不够聪明"，是结构性的：**参数是常量，常量不会自己更新**。

### 硬伤二：它没见过你的私有数据

企业内部的规章制度、你项目里的设计文档、客户合同——这些从来不在公开语料里。让模型回答"我们公司的报销上限是多少"，它只能编。

### 硬伤三：参数记忆是"模糊的"，不是"查得到的"

这一点最容易被忽略，也最重要。

模型记住一条知识的方式，是把千亿参数**调一调**，让它"倾向于"输出正确内容。这是一种**统计倾向**，不是一条可检索、可引用的记录。后果有两个：

1. 细节会串。它记得"某个 Python 特性限制并行"，但可能把 GIL 和 asyncio 的细节混在一起。
2. **你无法审计**。它答对了，你说不出它依据的是哪条语料；它答错了，你也定位不到错在哪。

```
参数记忆（微调/预训练）              外部知识库（RAG）
┌──────────────────────┐          ┌──────────────────────┐
│ 知识 = 千亿参数的倾向 │          │ 知识 = 一条条原文     │
│ 模糊、不可枚举        │          │ 精确、可枚举          │
│ 不可引用              │          │ 可引用、可审计        │
│ 更新 = 重新训练       │          │ 更新 = 改一条记录     │
└──────────────────────┘          └──────────────────────┘
```

**RAG 的答案就是第三条**：把知识从"参数里"搬到"上下文里"。

## 2. RAG 的本质：把闭卷改成开卷

LLM 有一个被严重低估的能力：**阅读理解**。

给它一段从没见过的文本，然后问关于这段文本的问题，它能答得很准。这个能力在预训练时就获得了，而且是**免费的**——不需要训练，只需要把文本放进 prompt。

于是有了这个思路：

```
闭卷（原始 LLM）:
  [问题] ──────────────→ LLM ──→ 靠参数里的模糊记忆作答

开卷（RAG）:
  [问题] ──→ 检索 ──→ [相关原文] ──┐
                                    ├─→ LLM ──→ 基于原文精确作答
  [问题] ───────────────────────────┘
```

**这一步视角转换解释了 RAG 的全部优缺点：**

| 观察 | 原因 |
|---|---|
| 回答精确、可引用 | 因为 LLM 是在"抄"你给的原文，不是在"回忆" |
| 知识更新成本极低 | 只需改知识库，模型一个字都不用动 |
| 能回答私有数据 | 私有数据只是被放进了 prompt |
| **效果上限由检索决定** | 检索没找到，LLM 就一定答不出——它只能读你给的东西 |
| **受上下文长度限制** | 书只能翻这么多页，塞不下就不能开卷 |

最后两条是 RAG 的真正瓶颈，也是为什么会有第 2 篇（切分）、第 4 篇（检索）、第 6 篇（优化）——**它们全都在优化"翻书"这个动作，而不是在优化模型**。

> 记住这个心智模型：**RAG 系统里，LLM 是负责"读"的，检索器是负责"找"的。找错了，读得再好也没用。**

## 3. 完整流程：两个阶段

RAG 有两个阶段，一个跑一次，一个每次都跑。这个不对称是理解整个系统的关键。

### 离线阶段（索引期）：只跑一次，或者文档更新时再跑

```
  原始文档            切分                向量化              存储
┌──────────┐      ┌──────────┐       ┌──────────┐      ┌──────────┐
│ PDF      │      │  块1     │       │ [0.12,..]│      │ 向量数据库│
│ Word     │─────→│  块2     │──────→│ [0.34,..]│─────→│  块1 → v1 │
│ Markdown │ 切块 │  块3     │ 编码  │ [0.56,..]│ 写入 │  块2 → v2 │
│ TXT      │      │  ...     │       │   ...    │      │   ...     │
└──────────┘      └──────────┘       └──────────┘      └──────────┘
                   (第2篇)             (第3篇)            (第3篇)
```

特征：**贵、慢、但只做一次**。所有文档都要跑一遍 embedding 模型。

### 在线阶段（查询期）：每问一次就跑一次

```
  用户问题          编码              检索              生成
┌──────────┐    ┌──────────┐    ┌──────────────┐   ┌──────────┐
│Python的  │    │[0.29,..] │    │ Top-K 块     │   │ 拼进     │
│GIL是什么？│───→│          │───→│  块2 (0.65)  │──→│ Prompt   │──→ LLM ──→ 回答
│          │编码│          │近邻│  块5 (0.63)  │   │          │
└──────────┘    └──────────┘    └──────────────┘   └──────────┘
                                  (第4篇)            (第5篇)
```

特征：**必须快**。用户在等着，这里每多 100ms 都是体验问题。

### 为什么这个划分重要

因为它决定了**优化该往哪里投**：

- 离线阶段慢一点没关系（几分钟建好索引，用一个月）。所以可以上大模型、可以跑多轮、可以加各种预处理。
- 在线阶段每 100ms 都要抠。所以**不能**在这里跑大模型重排序（除非你愿意等）。

> 这个不对称在第 6 篇会兑现：**HyDE（先让 LLM 生成假设答案再检索）把一次 LLM 调用插进了在线阶段**，检索质量可能变好，但延迟明显变差。这是用时间换质量，不是白捡的优化。

## 4. RAG vs 微调：本质区别是"知识存在哪"

两者经常被摆在一起比较，但比较的维度应该是**知识存放在哪里**。

```
微调：把知识烧进参数里
  [语料] ──训练──→ [模型参数被修改] ──→ 知识存在于权重中

RAG：把知识放在模型外面
  [语料] ──索引──→ [向量数据库]     ──→ 知识存在于数据库里
                        ↑
                    模型参数完全不变
```

| 对比 | RAG | 微调 |
|---|---|---|
| 知识存放位置 | 外部向量库 | 模型参数 |
| 更新一条知识 | 改一条记录，秒级生效 | 重新训练，小时级 |
| 单次调用成本 | 高（prompt 里塞了原文，token 变多） | 低（prompt 很短） |
| 一次性成本 | 低（只需跑 embedding） | 高（需要 GPU 训练） |
| 可解释性 | 好，能指到原文 | 差，说不清依据 |
| 上下文长度 | **受限制**（塞不下就不能开卷） | 不受限制 |
| 适合做什么 | 知识问答、文档助手、事实查询 | 风格定制、格式约束、能力注入 |

### 一句话判断该用哪个

- **"模型不知道某件事"** → 用 RAG。因为这是"缺知识"，补知识最快的方式是喂给它。
- **"模型知道，但做不好"** → 用微调。比如固定输出 JSON 格式、模仿特定文风、学会某种推理模式。这类是"缺能力/缺行为"，塞多少原文都没用。

> 一个常见的误区是把两者对立起来。实际上它们**互补**：微调让模型更擅长"读"（更好地遵循指令、更稳定地引用来源），RAG 让模型"有书可读"。真要做产品，通常是 **RAG 打底 + 微调优化阅读行为**。

## 5. 回到第 0 节：为什么 Top-1 会排错

这是本文最有价值的一节，因为它用真实数字说明了"检索不可靠"的具体形态。

我用同一个模型（`BAAI/bge-small-zh-v1.5`）把 5 条文档全部编码，算了它们与问题 `Python的GIL是什么？` 的余弦相似度：

| 排名 | 余弦相似度 | 距离 `2−2cos` | 文档 |
|---|---|---|---|
| 1 | **0.6616** | 0.6769 | 装饰器是一种修改函数行为的语法糖… |
| 2 | **0.6541** | 0.6917 | GIL（全局解释器锁）限制了多线程的并行执行… |
| 3 | 0.6206 | 0.7588 | Python 是一种高级编程语言，由 Guido 创建… |
| 4 | 0.5802 | 0.8396 | FastAPI 是一个现代 Python Web 框架… |
| 5 | 0.5759 | 0.8482 | PyTorch 是 Meta 开发的深度学习框架… |

**第 1 名和第 2 名的差距是 0.0075。** 这个差距小到没有任何实际意义——模型只要有一点噪声，排序就会翻转。

更要命的是这个数字：

```
5 条文档的余弦相似度全部落在 [0.5759, 0.6616] 区间内
极差 = 0.6616 − 0.5759 = 0.0857
```

也就是说，**"最相关"和"最不相关"的文档，相似度只差 0.0857**，全部挤在 0.58~0.66 这个很窄的带子里。这不是模型坏了，这是短文本 embedding 的**固有现象**：

1. 文档太短（这 5 条只有 44~57 个字符），语义信息量少，向量区分度天然就低。
2. 所有文档**共享大量词汇**（都含"Python"，而"的/是/了"这类字每篇都有），可以说它们"长得都挺像"。
3. 小模型（`bge-small` 只有 512 维、约 2400 万参数）的表达能力有限。

**这带来三个必须记住的结论：**

### 结论一：不要把"相似度"当成"相关性"的绝对度量

0.65 不代表"很相关"，0.58 也不代表"不相关"。**相似度只在同一批候选之间做相对排序时有意义，跨查询、跨数据集都不可比。**

> 这一条直接推翻了网上大量的"阈值过滤"写法。第 4 篇会用同一个小库、同一个查询，实测出"绝对阈值"为什么必然失效，并给出正确做法。

### 结论二：短文档 + 小模型 = 排序脆弱

0.0075 的差距意味着**只要多塞进去一条无关文档，或者换一个字，Top-1 就可能换人**。所以真正要靠的是：

- 取 `k=3~5` 而不是 `k=1`，给排序错误留冗余（第 0 节就是这么侥幸答对的）
- 用 MMR、混合检索等手段降低单点失败的风险（第 4 篇）

### 结论三：检索和生成要分开评估

这个案例里，"检索准确率"是 50%（Top-1 错了），但"最终回答正确率"是 100%。如果只看最终答案，你会以为系统没问题。**必须能单独看到检索结果**——这就是第 5 篇要给答案加"来源追溯"的原因。

## 6. 核心组件与它们的分工

| 组件 | 输入 → 输出 | 在系统里负责什么 | 本篇/后续 |
|---|---|---|---|
| 文档加载器 | 文件 → `Document` | 把各种格式统一成"文本 + 元数据" | 第 2 篇 |
| 文本切分器 | 长文本 → 多个块 | 决定**检索的最小单位** | 第 2 篇 |
| Embedding 模型 | 文本 → 向量 | 把语义映射到可比距离的空间 | 第 3 篇 |
| 向量数据库 | 向量 → Top-K | 快速找最近邻 | 第 3 篇 |
| 检索策略 | 查询 → 候选集 | 决定**哪些块进入 prompt** | 第 4 篇 |
| Prompt 模板 | 问题 + 上下文 → prompt | 约束 LLM 只用给定资料 | 第 5 篇 |
| LLM | prompt → 回答 | 阅读理解 + 组织语言 | 第 5 篇 |

代码里对应的就是一个 10 行的流水线（见 `1_rag_overview.py` 的 `demo_minimal_rag`）：

```
① 准备 Document
② RecursiveCharacterTextSplitter(chunk_size=200, chunk_overlap=20) 切分
③ Chroma.from_documents(chunks, embeddings) 向量化并入库
④ vectorstore.similarity_search(query, k=2) 检索
⑤ ChatOpenAI(...).invoke(prompt) 生成
```

注意 `chunk_size=200` 在这里其实**没起作用**——5 条文档每篇 44~57 字，本来就小于 200，切分器什么都没切（输出 "5 → 5 块"）。**参数不是设了就有用，得看数据形态**（第 2 篇详细讲过这个坑）。

## 7. 应用场景与不适用场景

**适合**（知识明确、需要引用、更新频繁）：

- 企业知识库问答（规章制度、产品手册）
- 文档助手（PDF / Word / Markdown 问答）
- 客服系统（话术库 + 工单历史）
- 代码库问答（把源码切成块后检索）
- 强监管领域的问答（法律、医疗、金融——因为**答案必须可追溯**）

**不适合**（这些是微调或别的手段的活）：

- 要求模型学会一种全新的推理方式 → 微调
- 要求严格的输出格式/风格 → 微调 + 约束解码
- 数据量大到塞不进上下文（比如全文检索整个代码仓库找一处调用） → 这该用传统检索/索引，不是 RAG
- 需要实时计算（"现在几点了""算一下 1234×5678"） → 调工具，不是 RAG

> 最后一条值得强调：**RAG 解决的是"知识不在模型里"的问题，不解决"模型不会算"和"模型做不到"的问题**。把不该 RAG 的任务硬塞进 RAG，是常见的设计错误。

## 代码

`1_rag_overview.py` 用一个函数演示完整流程，分五步：

| 代码位置 | 做什么 | 对应本文 |
|---|---|---|
| `demo_minimal_rag` 第 1 步 | 手写 5 条 `Document` | 第 6 节的组件表 |
| 第 2 步 | `RecursiveCharacterTextSplitter(chunk_size=200, chunk_overlap=20)` | 第 6 节末的提醒：本例中它没生效 |
| 第 3 步 | `Chroma.from_documents(chunks, embeddings)` | 离线阶段 |
| 第 4 步 | `similarity_search(query, k=2)` | 在线阶段；第 5 节解释了 k=2 为什么"救"了这次问答 |
| 第 5 步 | `ChatOpenAI(...).invoke(prompt)` | 开卷考试的"读" |

运行前需要准备 `.env`（模型名与 API Key 从环境读取）：

```
OPENAI_API_KEY=你的密钥
OPENAI_BASE_URL=你的兼容端点
OPENAI_MODEL=你的模型名
EMBEDDING_MODEL=BAAI/bge-small-zh-v1.5
```

Embedding 用的是**本地模型**（首次运行会自动下载约 100MB），不走 API。如果你直连 huggingface.co 超时，在 `.env` 里加上 `HF_ENDPOINT=https://hf-mirror.com`。

```bash
python 1_rag_overview.py
```

输出即第 0 节展示的内容——**请务必自己跑一次**，亲眼看一次"Top-1 排错了但答案对了"，比读十遍本文都管用。
