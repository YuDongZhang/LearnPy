# 6. RAG 优化技巧

> 这一篇回答一个问题：**那些"高级技巧"到底值不值得上？**
>
> 本篇的结论会让你意外，因为它是**实测出来的**：
>
> ```
> 查询改写、多查询、HyDE —— 在这套 5 条文档的小库上
> 三个技巧产出的检索结果，与"什么都不做"完全相同。
>
> 而延迟从 0.01 秒涨到 3.14 秒 / 4.09 秒。
> ```
>
> 所以本篇真正想讲的不是"有哪些技巧"，而是：
>
> ```
> 优化的顺序应该是：先有评估 → 发现瓶颈 → 再选技巧
> 而不是：先上技巧 → 感觉变好了 → 收工
> ```
>
> 网上大量教程直接罗列"十大 RAG 优化技巧"，**却不告诉你它们什么时候无效、代价是多少**。本文会用真实数字把代价标出来。
>
> 本文数字来自 `6_rag_optimization.py` 的实跑输出，以及一组测量延迟和 token 的实测（脚本已删除，均可复现）。

## 0. 先看真实运行

```
1. 查询改写
============================================================
原始查询: python怎么搞并发
改写后: Python中实现并发编程有哪些方式（多线程、多进程、异步IO）？各自的适用场景和限制是什么？

原始检索: ['Python的GIL限制多线程并行，CPU密集型任务用mul', 'asyncio是Python的异步编程库，使用async/a']
改写检索: ['Python的GIL限制多线程并行，CPU密集型任务用mul', 'asyncio是Python的异步编程库，使用async/a']
                ↑ 和上一行完全一样

2. 多查询检索
============================================================
原始问题: Python并发编程有哪些方案？
扩展查询:
  Python中实现并发编程可以采用哪些方式？ → 2 个结果
  针对不同应用场景，Python并发编程有哪些可选的技术方案？ → 2 个结果
  如何从底层机制上理解Python的并发编程解决方案（如多线程、多进程、异步等）？ → 2 个结果

合并去重: 6 → 3 个文档            ← 3 路召回 6 条，去重后只剩 3 条

3. HyDE
============================================================
问题: Python怎么做异步编程？
假设答案: Python 异步编程主要用 `asyncio` 库和 `async`/`await` 语法：
          - 用 `async def` 定义协程函数 ...

原始检索: ['asyncio是Python的异步编程库，使用async/a', 'Python的GIL限制多线程并行，CPU密集型任务用mul']
HyDE检索: ['asyncio是Python的异步编程库，使用async/a', 'Python的GIL限制多线程并行，CPU密集型任务用mul']
                ↑ 和上一行完全一样
```

**三处"完全一样"。** 查询改写、HyDE 各自做了那么多事，检索结果一个字符都没变。多查询更尴尬：**三个"不同角度"的查询，召回 6 条、去重后只剩 2~3 条**——说明三个查询召回的基本是同一批文档。

> ⚠️ **一个关于可复现性的提醒**：上面这段输出里，**凡是由 LLM 生成的文本（"改写后"的查询、三条"扩展查询"、HyDE 的"假设答案"）每次运行都不一样**——即使 `temperature=0`，服务端实现也不保证逐字节确定。**而检索命中的文档、以及"原始 == 改写"这个结论，是稳定复现的。** 所以本文涉及"跑一次可能变"的数字（去重条数、子查询长度）都会同时给出两次实测的结果。

这不是脚本写错了。这是**真实的、可以解释的**结果，第 6 节会分析原因，第 5 节会给出代价。

## 1. 先立规矩：优化必须有评估，否则就是在猜

第 4 篇已经给过检索侧的指标（Hit Rate / MRR / Recall@k），这里补上"优化的正确姿势"：

```
          ❌ 常见的错误顺序                ✅ 正确顺序
   ┌──────────────────────┐       ┌──────────────────────┐
   │ 听说 HyDE 很火        │       │ ① 建立评估集          │
   │ → 加上               │       │   (20~100 条问答对)   │
   │ → 感觉好了一点        │       │        ↓             │
   │ → 上线               │       │ ② 测出基线指标        │
   └──────────────────────┘       │   Hit Rate@3 = ?     │
                                  │        ↓             │
   问题：                          │ ③ 看失败案例，找瓶颈   │
   - "感觉好了一点"是多好？         │   (检索不到？噪点多？) │
   - 换一批问题还好吗？            │        ↓             │
   - 代价是什么？                  │ ④ 针对性选技巧        │
                                  │        ↓             │
                                  │ ⑤ 重测，只保留有效的   │
                                  └──────────────────────┘
```

**为什么强调这件事？** 因为本文第 0 节的输出就是最直接的证据：**三个被广泛推荐的技巧，在一套特定数据上一个都没生效。** 如果只靠"感觉"，你会把它们当成"必经之路"全部堆上去，付出 400 倍延迟，拿到零收益。

> **优化的第一步不是优化，是能测量。** 没有评估集，就永远不知道自己在改进还是在瞎忙。

## 2. 查询改写

### 原理：拉平"用户说话"和"文档写法"的差距

用户的提问和文档的表述，常常在**用词和句式**上差得很远：

| 用户会问 | 文档里写的 |
|---|---|
| `python怎么搞并发` | `Python 的 GIL 限制了多线程并行执行` |
| `这玩意儿怎么变快` | `性能优化：使用缓存减少重复计算` |
| `报错了咋办` | `异常处理与错误排查` |

用户的**口语**和文档的**书面术语**在向量空间里未必靠得近（虽然 embedding 能处理一部分同义，但口语化程度越高越吃力）。

查询改写的做法：**用 LLM 把口语化问题翻译成文档风格的技术查询**，再用改写后的查询去检索。

```
┌─────────────────────────────────────────────────────┐
│  "python怎么搞并发"                                   │
│          ↓  LLM 改写                                 │
│  "如何在Python中实现并发编程？请比较多线程、多进程      │
│   和异步IO的适用场景及具体实现方法。"                   │
│          ↓  embedding + 检索                         │
│  [GIL 文档, asyncio 文档]                             │
└─────────────────────────────────────────────────────┘
```

### 实测：在本例中无效

```
原始查询: python怎么搞并发
  检索 → [GIL 文档, asyncio 文档]

改写后查询: 如何在Python中实现并发编程？请比较多线程、多进程和异步IO的适用场景及具体实现方法。
  检索 → [GIL 文档, asyncio 文档]      ← 顺序完全相同，一个都没换
```

`python怎么搞并发` 这个查询已经很明确了（"并发"就是关键词），改写只是把它**变长**，没有引入新的检索信号。

### 代价是真实的

| 项 | 数值 |
|---|---|
| 原始查询长度 | 11 字符 / **9 token** |
| 改写后长度 | 38 字符 / **33 token**（3.7 倍） |
| **LLM 改写耗时** | **2.55 秒** |

**这是纯增成本**：在线阶段（第 1 篇讲过，用户正在等待）凭空插入一次 LLM 调用。

### 风险：改写可能"跑偏"

改写靠 LLM 理解意图，所以它**可能理解错**。例如把 `这个报错怎么解决` 改写成 `Python 异常处理最佳实践`——从"具体问题"变成了"泛泛主题"，**检索结果反而更宽泛、更没用**。

**这是查询改写最大的隐患：它会静默地降低精度，而你看不出来。** 所以改写后**必须对比检索结果**（`6_rag_optimization.py` 里 r1/r2 的对比就是为此），不能盲信。

### 什么时候值得用

| 值得 | 不值得 |
|---|---|
| 用户输入是**口语/错别字/极短**（客服、搜索框） | 查询已经是规范技术问句 |
| 查询里有**代词/省略**（"它怎么用"） | 查询含明确专有名词 |
| 需要处理**多语言**混输 | 小库（召回池 ≤ 几十条） |

## 3. 多查询检索

### 原理：一次提问只覆盖一个语义方向

一个查询在向量空间里只对应**一个点**。而用户的问题往往有**多个相关面**：

```
问题: "Python并发编程有哪些方案？"

         这个问题在语义空间里是"一个点"
                      ↓
     ┌────────────────┼────────────────┐
     ↓                ↓                ↓
  "多线程"方向      "多进程"方向      "异步IO"方向
     ↓                ↓                ↓
  召回 threading    召回 multiprocessing  召回 asyncio
     └────────────────┼────────────────┘
                      ↓
            合并 + 去重 → 送给 LLM
```

多查询的做法：**让 LLM 把一个问题改写成 N 个不同角度的查询，各自检索，然后合并去重**。目的是**提高召回率**（第 4 篇讲过：召回宁滥勿缺）。

### 实测：收益有限，去重后只剩 2~3 条

```
扩展查询:（一次运行）
  Python中实现并发编程可以采用哪些方式？                                  → 2 个结果
  针对不同应用场景，Python并发编程有哪些可选的技术方案？                   → 2 个结果
  如何从底层机制上理解Python的并发编程解决方案（如多线程、多进程、异步等）？ → 2 个结果

合并去重: 6 → 3 个文档              （另一次运行是 6 → 2）
```

**3 路查询共召回 6 条，去重后只剩 2~3 条。** 也就是说，**三路召回的内容高度重叠**。

原因很直接：**LLM 生成的三个"不同角度"查询，在语义上其实高度雷同**。看另一次运行的三行原文：

```
Python并发编程的实现方式有哪些？
如何选择Python多线程、多进程和异步编程？
Python处理高并发任务有哪些常见技术？
```

它们都是"Python + 并发 + 方案"的换皮，**没有一个是真正的新角度**（比如"GIL 对并发的限制""asyncio 的事件循环机制"）。在**主题非常集中**的小数据集上，LLM 也很难生成真正发散的查询——因为能发散的方向本来就少。

### 代价

| 项 | 数值 |
|---|---|
| LLM 生成 3 个查询耗时 | **2.23 秒** |
| 子查询长度 | 实测 30~32 字符 / **24~26 token**；另一次运行 22~41 字符（各 1 次 embedding） |
| 检索次数 | 从 1 次变成 **3 次**，再加一次合并去重 |

**多查询是"用延迟换召回"。** 只有在召回确实是瓶颈时（正确答案根本不在候选集里）才有意义。可以用第 4 篇的 **Recall@k** 判断：如果 `Recall@10` 已经接近 1.0，说明能召回的早召回了，**多查询不会带来任何提升**。

### 正确用法

```python
# 关键是：给 LLM 一个【发散】的指令，而不是"换个说法"
prompt = ChatPromptTemplate.from_template(
    "把下面的问题拆成 3 个【互补的、不重叠的】检索角度。"
    "每个角度要覆盖问题的一个不同侧面，而不是换同义词。"
    "每行一个查询：\n{question}"
)
```

并且**要做合并去重**（去重本身就是在度量发散程度：`去重前/去重后` 的比值越大，说明发散越好；本案例 `6→2` 或 `6→3`，即比值只有 2~3，说明发散失败）。

## 4. HyDE（假设文档嵌入）

### 原理：查询和文档之间有一道"表达鸿沟"

这是三个技巧里原理最巧妙的一个，值得讲清楚。

**问题所在**：embedding 模型的训练数据主体是**文档-文档**配对（或至少是同类文本）。所以它擅长判断"两段文档像不像"，但对"**一个疑问句**和一段**陈述句**像不像"的判断能力要弱一些。

```
   查询侧（疑问、口语、短）          文档侧（陈述、术语、长）
   ┌────────────────────┐          ┌────────────────────────┐
   │ Python怎么做异步编程？│          │ asyncio是Python的异步   │
   │                    │   ↕？     │ 编程库，使用async/await │
   │  11 token          │          │ 语法。                  │
   └────────────────────┘          └────────────────────────┘
        这两边"长相"完全不同，在向量空间里天然有偏移
```

**HyDE 的做法：先用 LLM 写一段"假装的答案文档"，然后用这段假文档去检索。**

```
   "Python怎么做异步编程？"
            ↓  LLM 生成假设答案（HyDE）
   "Python 异步编程主要通过 asyncio 库和 async/await 语法实现。
    核心是事件循环（Event Loop），它调度协程……"
            ↓  用这段【文档风格】的文字去检索
   命中文档 → 语义匹配变成"文档 ↔ 文档"，绕开了表达鸿沟
```

**关键洞察：检索时真正需要的是"位置"，不是"问题本身"。** 只要能把查询定位到文档空间中"正确答案所在的那片区域"，用什么文字去定位都行。而"一段编造的答案"天然落在正确答案附近——**因为它就在描述那些文档的内容**。

### 实测：在本例中无效

```
问题: Python怎么做异步编程？
假设答案: Python 异步编程主要通过 `asyncio` 库和 `async/await` 语法实现。核心是事件循环…

原始检索: ['asyncio是Python的异步编程库…', 'Python的GIL限制多线程并行…']
HyDE检索: ['asyncio是Python的异步编程库…', 'Python的GIL限制多线程并行…']
                ↑ 完全相同
```

原因和查询改写一样：**原始查询已经足够明确**。`Python怎么做异步编程` 里的 "Python"、"异步编程" 都是文档里的原词，表达鸿沟几乎不存在，所以 HyDE 没有改进空间。

### 代价（三个技巧里最贵的）

| 项 | 数值 |
|---|---|
| 原始问题 | 14 字符 / **11 token** |
| 假设答案 | 214 字符 / **130 token**（**12 倍**，该长度随生成内容浮动） |
| **LLM 生成耗时** | **3.71 秒** |
| embedding 耗时（短查询） | **7.6 ms** |
| embedding 耗时（假设答案） | **21.3 ms**（2.8 倍） |

**HyDE 的成本是双份的**：既要多一次 LLM 调用（3.71 秒），又让 embedding 的输入变长 12 倍（检索变慢 2.8 倍）。而它只解决"表达鸿沟"这一类问题。

### 风险：假设答案跑偏

HyDE 有个**内在悖论**：

```
HyDE 假设：LLM 能写出一段接近正确答案的文字
但如果我们已经能正确回答这个问题了，为什么还需要检索？
```

**它依赖"模型大致知道这个领域，只是细节不准"。** 如果问题在模型的完全陌生领域（比如你公司的内部系统代号），LLM 生成的"假设答案"会是**纯粹的编造**，而它会把检索带到一个**完全错误**的语义区域——**比原始查询更差**。

> 所以 HyDE 的适用判断很明确：**模型"知道大概、不懂细节"**时有效；**模型完全不懂**时有害。这需要在你的数据上实测。

## 5. 代价总表：这是本篇最该记住的一张表

同一批文档、同一个问题（`Python怎么做异步编程？`），三条路径端到端计时：

| 方案 | 端到端耗时 | 检索结果 | 相对成本 |
|---|---|---|---|
| **① 纯向量检索** | **0.01 秒** | asyncio, GIL | 1× |
| **② 查询改写 + 检索** | **3.14 秒** | asyncio, GIL | **314×** |
| **③ HyDE + 检索** | **4.09 秒** | asyncio, GIL | **409×** |

```
┌──────────────────────────────────────────────────────────┐
│  延迟涨了 314 倍和 409 倍，检索结果一个字符都没变。          │
│                                                          │
│  这就是"先上技巧"的代价：你会为一个不存在的收益付费。        │
└──────────────────────────────────────────────────────────┘
```

**延迟拆解**（在线阶段，用户正在等待）：

```
纯向量检索   ▏0.01s
查询改写     ████████████████████████████▏ 3.14s   (LLM 改写 2.55s + 检索)
HyDE        █████████████████████████████████████▏ 4.09s  (LLM 生成 3.71s + 更慢的 embedding)
```

**第 1 篇讲过的那个不对称在这里兑现了**：RAG 的在线阶段对延迟极其敏感，而这些优化技巧的共同点就是**往在线阶段插 LLM 调用**。

> 一个重要的设计启示：**如果非要上这类技巧，尽量把它们挪到"离线"或"可缓存"的位置。**
> 例如：把高频查询的改写结果**缓存**起来；或者把多查询的"扩展"放到前端交互时（用户还在打字/思考）预跑。**不一定要串在用户按键后的那条路径上。**

## 6. 为什么在这里全都没生效

这是本篇的核心分析。三个技巧**都不是坏技巧**，它们在特定条件下确实有效。本例之所以全部无效，有三个具体原因：

### 原因一：召回池太小，没有腾挪空间

```
库里的文档总数: 5 条
我们每次取: k = 2 条

→ 任何查询都只能在 5 条里挑 2 条
→ 而这 5 条主题高度集中（全是 Python 并发相关）
→ 所以"换一种查询措辞"几乎不可能改变挑选结果
```

**当候选池只有 5 条、且全部大致相关时，排序结果对查询的细微变化是"不敏感"的。** 换个说法，检索结果还是那 2 条。

### 原因二：库的主题太集中，语义区分度靠 embedding 就够了

这 5 条文档分别是 GIL、asyncio、threading、concurrent.futures、装饰器。**前 4 条彼此相关，第 5 条（装饰器）明显无关**。

在这种"要么很相关要么很不相关"的分布下，**基础向量检索已经能把它们分开**——第 4 篇的实测证明了这一点（`装饰器怎么用` 查询下，装饰器文档 `score = 0.9975`，其余都在 1.26 以上，差距明显）。

**优化技巧解决的是"细粒度排序"问题**（几条都挺相关，谁更相关？）。而本例根本不需要细粒度排序。

### 原因三：查询本身已经足够明确

```
用户查询: "python怎么搞并发" / "Python怎么做异步编程？"
              ↓
   文档里就有 "GIL" / "asyncio" / "并发" / "异步编程" 这些原词
              ↓
   表达鸿沟 ≈ 0 → 改写 / HyDE 都没有发挥空间
```

**查询改写和 HyDE 都是用来"跨过表达鸿沟"的。本例没有鸿沟，所以它们无鸿沟可跨。**

### 反过来说：什么情况下它们会生效

| 条件 | 为什么会有效 |
|---|---|
| 库大（几千~几百万条），**召回是瓶颈** | 多查询、HyDE 能扩大召回面，把"本来不在 Top-K 里的正确答案"捞进来 |
| 查询极口语化 / 有错别字 / 有代词 | 改写能把它拉回文档术语空间 |
| 文档用**术语**，用户用**白话**（医疗、法律、金融） | HyDE 用文档风格的语言检索，跨过鸿沟 |
| 有一批"看起来都对、其实只有一条对"的文档 | 这时才轮到 Rerank / MMR 发挥作用 |

**共同点是：问题必须真实存在。** 所以第 1 节的评估流程不是形式主义——它是**判断"有没有问题"的唯一手段**。

## 7. 其他优化手段（按"性价比"排序）

前三个技巧都动"查询端"。下面是另外几类，性价比差异很大。

### 7.1 检索端：Rerank 重排序（性价比最高）

```
召回落 20~100 条  →  Rerank 模型重新打分  →  取 Top-3
   (快、糙)              (慢、准，只跑几十条)      (精)
```

**它和第 4 篇讲的"分数过滤 / MMR"解决的是同一类问题（排序），但可靠性高一个档次**，原因在于模型结构：

| | 双塔 Embedding | Rerank 模型 |
|---|---|---|
| 计算方式 | query 和 doc **各编各的**，再算距离 | query 和 doc **拼在一起**送进模型 |
| 能否看到交互 | ❌ 看不到词级对应关系 | ✅ 能看到每个词之间的关联 |
| 速度 | 快（doc 向量可预计算） | 慢（每对都要现算） |
| 用在哪 | **召回**（全库扫描） | **精排**（只跑几十条） |

**"能否看到交互"是关键。** 双塔模型必须在编码时就决定"这段文字代表什么"，而 Rerank 模型可以看着 query 去读 doc，所以它更准。代价是不能预计算，因此只能用在精排阶段。

### 7.2 生成端：上下文压缩

只把检索到的块里**与问题相关的句子**喂给 LLM。`.py` 里给的名字是"上下文压缩"。

**收益**：省 token、减噪音（第 2 篇讲过：每块都在消耗注意力预算）。
**代价**：需要一次 LLM 调用（或一个专门的抽取模型），仍是**在线阶段的开销**。
**风险**：压缩时可能把关键的那半句话删掉，导致 LLM 无法作答。

### 7.3 切分端：小块检索 + 大块生成（很巧妙）

```
检索阶段用【小块】           生成阶段用【大块】
┌──────────────┐            ┌────────────────────────────┐
│ 块1 (200字)  │ 命中       │ 返回块1所在的【父块】        │
│ 块2 (200字)  │ ────────→  │ 或 块1 ± 相邻块（共 800 字） │
│ 块3 (200字)  │            │                            │
└──────────────┘            └────────────────────────────┘
  小块：向量更锐利，            大块：上下文完整，
  检索更准                      LLM 答得完整
```

**它同时解决了第 2 篇里那对矛盾**（块太小 → 检索准但上下文破碎；块太大 → 上下文完整但向量被平均）。做法是：索引里存小块，但每个小块**记录自己属于哪个大块**，检索命中后返回大块。

工程上的关键点是**元数据要能指回父块**（`metadata={"parent_id": ...}`）——第 2 篇讲过 `metadata` 不参与向量检索，专门用来做这种挂载。

### 7.4 切分端：语义切分

不用固定长度切，而是**按语义边界**切（检测相邻句子的语义突变点作为切割位置）。

比 `RecursiveCharacterTextSplitter` 更贴近真实语义边界，但**需要跑 embedding 来算相邻句子的相似度**，所以建索引更慢、成本更高。

> **注意它属于"离线阶段"的开销**（第 1 篇的不对称）——一次性的慢，可以接受。这是它比查询改写"划算"的地方。

## 8. 决策表：什么时候该上什么

| 症状（要靠评估发现） | 该上的手段 | 属于哪个阶段 | 成本 |
|---|---|---|---|
| 正确答案**根本不在**候选集里 | 多查询、HyDE、提高 `fetch_k` | 在线 | 高（插 LLM） |
| 候选里有对的，但**排到了第 5、第 8** | Rerank、MMR | 在线（Rerank） | 中 |
| 搜**专有名词/错误码**搜不到 | 混合检索（BM25 + 向量） | 在线 | 低 |
| Top-3 全是同一段的重复 | MMR（`fetch_k` 调大） | 在线 | 无 |
| 上下文太长、噪音多 | 上下文压缩、减小 `k` | 在线 | 中 |
| 检索准但 LLM 答得碎 | 小块检索 + 大块生成 | **离线**改索引 | 一次性 |
| 检索边界切断了句子 | 语义切分、调整 `separators` | **离线** | 一次性 |
| LLM 用自己的知识瞎答 | 加强 Prompt 约束（第 5 篇） | 在线 | **几乎为零** |

**注意最后一行：性价比最高的优化，往往是最不起眼的那个——改 Prompt。** 它零成本、零延迟，而上一节实测的三个技巧要付出 300~400 倍延迟。

`6_rag_optimization.py` 分三节，对应本文的三种"查询端"技巧：

代码里的对比写法很关键，**每个技巧都保留了"改前/改后"两份结果**：

```python
r1 = db.similarity_search(original, k=2)      # 基线
r2 = db.similarity_search(rewritten, k=2)     # 优化后
print(f"\n原始检索: {[d.page_content[:30] for d in r1]}")
print(f"改写检索: {[d.page_content[:30] for d in r2]}")
```

**没有这个对比，你根本无法判断技巧有没有生效**——这正是第 1 节强调"可测量"的代码级体现。

> 另外注意 `build_db()` 用了模块级缓存。这是第 5 篇第 6 节那个 bug 的修复：修复前同一进程内三次 `build_db()` 会把库里塞成 15 条重复文档，导致"合并去重"输出成 `6 → 1`，**整个对比实验的结论都是错的**。

**建议动手改三处**，自己复现本文的结论：

1. **把文档数从 5 条扩到 200 条**（比如把 `docs` 复制扩充、或加载一个真实文档目录），再跑一次——观察多查询的"去重比"是否变好。这是验证第 6 节"召回池太小"最直接的方式。

2. **把 `k` 从 2 改成 5**，看查询改写是否还能保持"结果完全相同"——`k` 越大，检索对查询措辞越不敏感。

3. **给三次写法加计时**，自己量一遍 0.01s / 3.14s / 4.09s 的差距：

```python
import time
t0 = time.perf_counter()

print(f"纯检索: {time.perf_counter() - t0:.2f}s")
```
