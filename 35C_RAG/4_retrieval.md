# 4. 检索策略

> 这一篇回答一个问题：**"从向量库里捞出哪些块"这件事，有多少种做法，各自在什么情况下帮倒忙？**
>
> 主线一句话：
>
> ```
> 检索 = 先「召回」（别漏掉）→ 再「排序」（别排错）
> ```
>
> 本篇会用真实数据把三件事说透：
>
> 1. **带分数过滤**：`score > 0.7` 这个写法方向就是错的（第 3 节纠正），但改成 `<` 也**仍然不可靠**——我会用 4 个查询的真实分数分布证明"绝对阈值"为什么必然失效，并给出可用的替代方案。
> 2. **MMR** 的公式推导 + 逐轮手算真值，并揭示一个源码级细节：**Chroma 的 MMR 返回顺序不是 MMR 顺序**（第 4 节）。
> 3. **混合检索 / BM25**：用真实数字说明"关键词检索"到底补了什么（第 5 节）。
>
> 本文数字来自 `4_retrieval.py` 的实跑输出，以及一组用真实向量做的实测（脚本已删除，均可复现）。凡是手工设计的例子都会明确标注。

## 0. 先看真实运行

```
1. 基础相似度检索
查询: Python多线程有什么限制？
  [1] Python的GIL限制了多线程并行执行，CPU密集型任务建议用多进程。
  [2] Python的多线程适合IO密集型任务，如网络请求和文件读写。
  [3] multiprocessing模块可以绕过GIL限制，实现真正的并行计算。

2. MMR检索
MMR查询: Python的并发编程
  [1] Python的asyncio提供了异步编程支持，适合高并发IO操作。
  [2] Python的GIL限制了多线程并行执行，CPU密集型任务建议用多进程。
  [3] Python的装饰器是修改函数行为的语法糖，使用@符号。      ← 这个跟"并发"无关

3. 带分数过滤
带分数查询: 装饰器怎么用
  ✗ 分数: 0.9975 | Python的装饰器是修改函数行为的语法糖…     ← 正确答案，被 ✗ 了
  ✗ 分数: 1.2654 | Python的生成器使用yield关键字…
  ✗ 分数: 1.3669 | multiprocessing模块可以绕过GIL限制…
  ✗ 分数: 1.3975 | Python的GIL限制了多线程并行执行…

4. Retriever
Retriever结果: 3 个文档
  Python的asyncio提供了异步编程支持，适合高并发IO操作。...
  Python的生成器使用yield关键字，惰性产生值，节省内存。...
  Python的装饰器是修改函数行为的语法糖，使用@符号。...
```

三处值得立刻停下来看的地方：

1. **第 1 节检索得非常准**（GIL → 多线程 IO → multiprocessing，三条全对，排序也合理）。
2. **第 2 节 MMR 把"装饰器"排进了前 3**——它和"并发编程"毫无关系。这不是 bug，是 MMR 的**设计目标**（要多样性）在**小库上产生的副作用**。第 4 节会用逐轮手算说明它是怎么被选进来的，以及为什么这是个"帮倒忙"的案例。
3. **第 3 节全部是 ✗**。连最相关的"装饰器"文档（`score = 0.9975`）都被判定为不合格。第 3 节专讲这件事。

## 1. 检索在系统里的位置：召回与排序是两件事

先把两个概念分开，后面所有讨论都建立在这个划分上。

```
                     ┌─────────── 召回 (Recall) ───────────┐
全部文档  ──────────→│  尽可能"别漏掉"真正相关的文档        │───→ 候选集 (20~100 条)
                     └────────────────────────────────────┘
                                          │
                     ┌─────────── 排序 (Ranking) ──────────┐
                     │  把这些候选"按相关性排好序"           │───→ Top-K (3~5 条)
                     └────────────────────────────────────┘
                                          │
                                    拼进 Prompt 交给 LLM
```

这两个阶段的目标是**互相冲突**的，这是本章最核心的张力：

| 阶段 | 目标 | 手段 | 典型参数 |
|---|---|---|---|
| **召回** | 宁滥勿缺（别漏） | 放大 `k` / `fetch_k`、多路召回、混合检索 | `fetch_k=20~100` |
| **排序** | 宁缺勿滥（别错） | 减 `k`、MMR、Rerank、分数过滤 | `k=3~5` |

第 1 篇实测过一个具体后果：查询 `Python的GIL是什么？` 时，正确答案只排到**第 2 名**（余弦 0.6541 vs 装饰器的 0.6616，只差 0.0075）。**排序是脆弱的，所以召回阶段必须留冗余。**

## 2. 基础相似度检索：`similarity_search(query, k)`

就是把查询编码成向量，然后取最近的 k 个。

```python
results = db.similarity_search(query, k=3)
```

这是唯一一个"几乎不会出错"的检索方式——因为它的语义最简单明确：**给我最像的 k 条**。`4_retrieval.py` 第 1 节的输出也证明它在这批数据上工作得很好。

`k` 怎么定？这是本章最实际的权衡：

| `k` 太小（1~2） | `k` 太大（10+） |
|---|---|
| 排序错一次就全盘皆输（第 1 篇的 0.0075 差距） | 无关内容挤进 prompt |
| 上下文短，LLM 注意力集中 | 上下文长，token 成本上升 |
| 相关但表述不同的文档容易漏 | **LLM 被噪音干扰，容易抓错重点**（幻觉来源） |

**经验值 3~5**，但要靠第 7 节的评估指标在你自己的数据上验证，不要照抄。

> 顺带说明：`similarity_search` 是**纯排序**，它不控制"要不要返回"。即使库里全是无关文档，它也会忠实地返回最近的 k 条。所以"检索到东西"和"检索到有用的东西"是两回事——第 3 节就来解决这个。

## 3. 带分数过滤：方向错了，改对方向也不够

这是本篇最重要的一节，因为它是**唯一一处本教程文档与代码自相矛盾的地方**，而且网上抄错的版本流传极广。

### 3.1 先纠正方向：`score` 是距离，越小越相关

第 3 篇已经用真实数据把 Chroma 的 `score` 钉死了：

| `hnsw:space` | `score` 含义 | 越小越相关？ |
|---|---|---|
| `l2`（默认） | `2 − 2·cos` | ✅ |
| `cosine` | `1 − cos` | ✅ |

所以旧版文档里那句

```python
# ❌ 方向反了
filtered = [(doc, score) for doc, score in results if score > 0.7]
```

筛出来的是**最不相关**的那一批。

`4_retrieval.py` 里的代码方向是对的：

```python
status = "✓" if score < 0.5 else "✗"
```

**方向对了。但是——**

### 3.2 实测：`score < 0.5` 会丢掉全部结果

看第 0 节第 3 节的真实输出：4 条候选的分数是 `0.9975 / 1.2654 / 1.3669 / 1.3975`，**全部大于 0.5，全部被标成 ✗**。

这不是偶然。我把 6 条文档对 **4 个不同查询**的完整分数分布都测了出来（同一批文档、同一个模型、Chroma 默认 `l2` 空间）：

| 查询 | Top-1 的 `score` | 最差的 `score` | 分布极差 | Top-1 是否正确 |
|---|---|---|---|---|
| `装饰器怎么用` | **0.9975** | 1.6284 | 0.6308 | ✅ 装饰器 |
| `Python多线程有什么限制？` | **0.4097** | 0.9245 | 0.5148 | ✅ GIL |
| `Python怎么做异步编程？` | **0.5643** | 0.9714 | 0.4072 | ✅ asyncio |
| `怎么做红烧肉`（完全无关） | 1.4284 | 1.5594 | **0.1310** | ❌ 库里确实没有 |

**请重点看第 1、3 行的对比：**

```
同样都是"正确答案排在 Top-1"：
  查询 "Python多线程有什么限制？"  → Top-1 score = 0.4097
  查询 "装饰器怎么用"              → Top-1 score = 0.9975
                                     ─────────────────────
                                     相差 2.4 倍！
```

**同样是正确的命中，分数差了 2.4 倍。** 这就是第 3 篇那个结论的量化版本：**相似度的绝对值跨查询不可比**。

所以任何**绝对阈值**都必然在某个查询上崩掉：

| 阈值 | 后果 |
|---|---|
| `score < 0.5` | `装饰器怎么用`（0.9975）→ 全部丢弃，**有用的查询失败** |
| `score < 1.0` | `Python多线程有什么限制？`（最差 0.9245）→ 把 5 条噪音也放进来 |
| `score < 1.4` | `怎么做红烧肉`（1.4284）→ 把完全无关的结果全部放进来 |

**无论这个数字取多少，都会被某一类查询打脸。** 这就是为什么"调一个阈值"永远调不好。

### 3.3 可用的替代方案：看"分布的相对间隔"，而不是绝对值

上表里藏着一个非常干净的信号，把它单独拎出来看：

```
                    Top-1 score   Top-2 score   相对间隔 (s2−s1)/s1
相关查询：
  装饰器怎么用         0.9975        1.2654         26.9%   ← 第1名明显甩开第2名
  多线程有什么限制？    0.4097        0.5805         41.7%
  怎么做异步编程？      0.5643        0.7342         30.1%
无关查询：
  怎么做红烧肉         1.4284        1.4701          2.9%   ← 全都挤在一起
```

**这是一个可以落地的判据：**

```
┌──────────────────────────────────────────────────────────────┐
│ 不要问「分数够小吗？」                                          │
│ 要问「第1名比第2名好多少？」                                    │
│                                                              │
│   (score₂ − score₁) / score₁  <  10%   →  库里大概没有相关内容  │
│   (score₂ − score₁) / score₁  >  20%   →  第1名是个可信的命中   │
└──────────────────────────────────────────────────────────────┘
```

相关查询的相对间隔是 **26.9% ~ 41.7%**，无关查询只有 **2.9%** —— 中间有超过 8 倍的空档，判别起来毫不费力。

**为什么这个判据更稳？** 因为它做的是**相对比较**，天然抵消了"不同查询语义密度不同"带来的整体偏移（这正是第 3 篇讲的"绝对值不可比"问题）。这跟"归一化"能消除向量长度影响是同一个思路：**把不可比的绝对量，变成可比的相对量。**

### 3.4 更常用的做法：干脆不做过滤

实务里最省事、也最稳的做法是**放弃分数过滤**，改用两条路：

1. **固定取 Top-K，让 LLM 自己判断资料够不够。** 这靠在 Prompt 里明确写"如果资料中没有相关信息，请说'我不确定'"（第 5 篇的实测里，LLM 对"Go 语言怎么样？"确实回答了"我不确定"）。
2. **上 Rerank 模型。** 用一个专门的相关性模型（如 `bge-reranker`）对候选重打分。Rerank 模型直接输出"相关性分数"（**越大越相关**，语义明确），而且它同时看 query 和 document，比双塔 embedding 准得多。代价是慢，所以只对召回的几十条做。

| 方案 | 可靠性 | 成本 | 何时用 |
|---|---|---|---|
| 绝对阈值过滤 | **低** ❌ | 无 | 不建议 |
| 相对间隔判据 | 中 | 无 | 需要"拒答"能力时 |
| 交给 LLM 判断 | 中高 | 略增 prompt | **默认推荐** |
| Rerank 模型 | **高** | 明显增加延迟 | 对准确率要求高的场景 |

## 4. MMR：最大边际相关性

### 4.1 它想解决什么问题

`similarity_search` 有一个内生的缺陷：**它只看"和问题的相似度"，不看候选之间是否重复。**

假设库里同一段说明被切成了 5 块，内容高度重叠。那么 Top-3 很可能全是这 5 块的子集——**你花了 3 个 prompt 名额，却只得到 1 条信息**。这就是"相关但冗余"。

MMR（Maximal Marginal Relevance）的做法是给打分加一个**惩罚项**：候选如果和**已经选中的文档**很像，就扣分。

### 4.2 公式推导

```
MMR = argmax [ λ · sim(d, q)  −  (1 − λ) · max sim(d, s) ]
        d∈D\S             ↑                  s∈S     ↑
                    与查询的相关性              与已选集合的最大冗余
```

逐项拆开：

| 记号 | 含义 |
|---|---|
| `D` | 候选集（由 `fetch_k` 决定） |
| `S` | 已经选中的集合 |
| `D \ S` | 还没被选中的候选 |
| `sim(d, q)` | 候选 d 与**查询**的相似度（越大越好，第一项） |
| `max sim(d, s)` | 候选 d 与**已选中任意一条**的最大相似度（越大越冗余，第二项要减掉） |
| `λ`（`lambda_mult`） | 权衡旋钮，默认 **0.5** |

`λ` 的极端值给出清晰的直觉：

```
λ = 1.0  →  公式退化成纯相似度检索（完全不管冗余）
λ = 0.0  →  完全不看查询，只挑"最新奇的"候选（结果必然是垃圾）
λ = 0.5  →  相关性和多样性各占一半（默认值，也是本节的实测配置）
```

**这个公式有一个常被忽略的性质：第二项是减去的。** 所以当候选都很相似时，MMR 分数可以变成**负数**——本节的真实计算里就会出现负数，这是正常的。

### 4.3 逐轮手算（真实向量，λ = 0.5）

配置：查询 `Python的并发编程`，`k=3`，`fetch_k=6`，即从全部 6 条候选里挑 3 条。

**第 0 步：先算所有候选与查询的相似度**（真实值）

| 候选 | `cos(q, d)` | 文档 |
|---|---|---|
| d2 | **0.6914** | asyncio 提供了异步编程支持 |
| d0 | 0.6639 | GIL 限制了多线程并行执行 |
| d1 | 0.6390 | 多线程适合 IO 密集型任务 |
| d4 | 0.6179 | 生成器使用 yield |
| d3 | 0.6024 | **装饰器**是修改函数行为的语法糖 |
| d5 | 0.5374 | multiprocessing 可以绕过 GIL |

**第 1 轮**：`S = ∅`，公式第二项没有对象，直接选相似度最高的

```
选中 d2（asyncio），MMR = 0.6914
```

**第 2 轮**：`S = {d2}`，现在第二项生效了

| 候选 | `cos(q,d)` | `max sim(d, d2)`（冗余） | `MMR = 0.5·sim − 0.5·冗余` |
|---|---|---|---|
| **d3 装饰器** | 0.6024 | **0.5788** | **+0.011830** ← 选中 |
| d4 生成器 | 0.6179 | 0.6381 | −0.010082 |
| d0 GIL | 0.6639 | 0.6945 | −0.015294 |
| d5 multiprocessing | 0.5374 | 0.5950 | −0.028827 |
| d1 多线程 IO | 0.6390 | 0.7482 | −0.054619 |

手算核对第一行：

```
MMR(d3) = 0.5 × 0.6024 − 0.5 × 0.5788 = 0.3012 − 0.2894 = 0.0118  ✓ 与实测一致
```

**第 3 轮**：`S = {d2, d3}`

| 候选 | `cos(q,d)` | `max sim(d, {d2,d3})` | `MMR` |
|---|---|---|---|
| **d0 GIL** | 0.6639 | 0.6945 | **−0.015294** ← 选中 |
| d4 生成器 | 0.6179 | 0.6703 | −0.026168 |
| d5 multiprocessing | 0.5374 | 0.5950 | −0.028827 |
| d1 多线程 IO | 0.6390 | 0.7482 | −0.054619 |

**MMR 最终选择顺序：d2 → d3 → d0**（集合 `{d2, d3, d0}`）

### 4.4 这个案例暴露了 MMR 的代价

把 MMR 的选择和纯相似度的排名并排看：

```
纯相似度排名:  d2(0.6914) → d0(0.6639) → d1(0.6390) → …
                          ↑
                    第2相关的是 GIL，跟"并发编程"高度相关

MMR 选择:      d2(0.6914) → d3(0.6024) → d0(0.6639)
                          ↑
                    GIL 被挤到第3，换上来的是「装饰器」
                    装饰器跟"并发编程"没有任何关系
```

**发生了什么？** 回顾第 2 轮的表：

- `d0`（GIL）的查询相似度是 **0.6639**，比 `d3`（装饰器）的 **0.6024** 高得多。
- 但 `d0` 和第 1 轮选中的 `d2`（asyncio）**太像了**：冗余度 **0.6945**。
- `d3` 和第 1 轮选中的 `d2` **很不一样**：冗余度只有 **0.5788**。
- 于是 MMR 分数反超：`d3` 的 **+0.0118** > `d0` 的 **−0.0153**。

**MMR 用"相关性"换了"多样性"。而这次交易是亏的**——因为库里只有 6 条文档、主题本来就各不相同，冗余问题**根本不存在**。MMR 为了解决一个不存在的问题，牺牲了实实在在的相关性。

> **这一节最该记住的结论**：MMR 解决的是"**候选之间高度重复**"的问题。如果：
>
> - 文档块都很短、主题互不相同 → **别用 MMR**（本案例就是）
> - 库里同一份内容被切成了很多块 → **用 MMR**，它能把名额让给不同角度
>
> 判断标准是 `fetch_k` 条候选里的**平均两两相似度**。相似度普遍高（> 0.8）才说明冗余严重。**不要因为它叫"最大边际相关性"听起来高级就默认开着。**

### 4.5 一个源码级细节：返回顺序不是 MMR 顺序

我在核对时发现手算的 MMR 顺序和 Chroma 的返回顺序对不上，追进源码找到了原因。`langchain_community/vectorstores/chroma.py` 里 MMR 的最后一步是：

```python
mmr_selected = maximal_marginal_relevance(...)   # 返回被选中的【下标】
candidates = _results_to_docs(results)           # 按【距离】排好序的候选

selected_results = [r for i, r in enumerate(candidates) if i in mmr_selected]
```

注意最后一行：它遍历的是 **`candidates`（按距离排序的候选列表）**，判断"这个下标有没有被 MMR 选中"，然后按遍历顺序收集。

**它用的是"是否被选中"，而不是"被选中的顺序"。** 所以最终返回的顺序是**距离顺序**，不是 MMR 的选择顺序。

实测印证：

```
MMR 选择顺序:        [2, 3, 0]   (asyncio → 装饰器 → GIL)
Chroma 实际返回顺序: [2, 0, 3]   (asyncio → GIL → 装饰器)
                     ↑ 按距离排：d2(0.6914) > d0(0.6639) > d3(0.6024)
```

**实际影响**：如果你以为"返回的第 1 条是 MMR 打分最高的"，这个假设不成立。返回的集合是对的，**顺序只反映距离**。在需要严格按 MMR 分数取前几条时（比如只取第 1 条），要意识到这一点。

## 5. 混合检索与 BM25

### 5.1 向量检索的两个真实盲区

向量检索靠"语义"，这在处理自然语言时是优势，但对**精确串**是劣势：

| 场景 | 向量检索 | 关键词检索 |
|---|---|---|
| "GIL 是什么" | ✅ 能匹配到 GIL 相关段落 | ✅ |
| 查错误码 `ERR_4032` | ❌ 可能匹配到其他错误码 | ✅ 精确命中 |
| 查函数名 `max_marginal_relevance_search` | ❌ 会被拆成语义相近的内容 | ✅ |
| 查"并发编程有哪些方案" | ✅ 能召回 asyncio / threading | ❌ 字面对不上就漏 |

第二种情况是硬伤：**专有名词、ID、错误码、型号——这些"没有语义、只有字面"的东西，向量检索天然不擅长。**

### 5.2 BM25 公式与它的精髓

BM25 是关键词检索的经典算法，`k1` 和 `b` 是两个调节参数（常用 `k1=1.5`、`b=0.75`）。

```
score(D, Q) = Σ   IDF(t) ·  ──────────────────────────────────
             t∈Q              f(t,D) + k1 · (1 − b + b · |D|/avgdl)

                    f(t,D) · (k1 + 1)


其中  IDF(t) = ln( 1 + (N − n(t) + 0.5) / (n(t) + 0.5) )

      N     = 文档总数
      n(t)  = 包含词 t 的文档数
      f(t,D)= 词 t 在文档 D 里出现的次数
      |D|   = 文档 D 的长度
      avgdl = 所有文档的平均长度
```

**BM25 最漂亮的地方就在 `IDF` 上。** 我用 6 条文档、`k1=1.5, b=0.75` 实测（`N=6`、`avgdl=21.2`）：

**查询 `Python的并发编程`，分词为 `[Python, 的, 并, 发, 编, 程]`：**

| 词 `t` | 出现在几篇文档 `n(t)` | `IDF(t)` | 说明 |
|---|---|---|---|
| Python | 5 | 0.2412 | 到处都是 → 权重低 |
| **的** | **6** | **0.0741** | **每篇都有 → 权重几乎为 0** |
| 并 | 3 | 0.6931 | |
| 发 | 1 | **1.5404** | 很稀有 → 权重最高 |
| 编 | 1 | **1.5404** | |
| 程 | 3 | 0.6931 | |

**`"的"` 的 IDF 是 0.0741，只有 `"发"`（1.5404）的二十分之一。**

这意味着：**BM25 自动完成了"停用词降权"——不需要手工维护停用词表。** "的""了""是"这类虚词因为到处出现，IDF 天然趋近 0，对总分几乎没有贡献。

注意 `IDF = ln(1 + (N − n + 0.5)/(n + 0.5))` 这个形式：当 `n = N`（每篇都有）时，括号内是 `1 + 0.5/(N+0.5)`，`ln` 后是个很小的正数——**永远不会变负**。这就是公式里那个 `1 +` 的作用，避免"文档数等于词频数"时 ID 变成负权重。

### 5.3 BM25 的真实排名

| 查询 `Python的并发编程` | BM25 分数 | 文档 |
|---|---|---|
| 第 1 名 | **4.9041** | asyncio 提供了异步编程支持，适合高并发 IO |
| 第 2 名 | 1.8682 | GIL 限制了多线程并行执行 |
| 第 3 名 | 0.9706 | 多线程适合 IO 密集型任务 |
| 第 4 名 | 0.8043 | multiprocessing 可以绕过 GIL |

| 查询 `装饰器怎么用` | BM25 分数 | 文档 |
|---|---|---|
| 第 1 名 | **4.9258** | 装饰器是修改函数行为的语法糖 |
| 第 2 名 | 1.7666 | 生成器使用 yield |
| 第 3 名 | 0.6409 | GIL 限制了多线程并行执行 |

两次查询的 Top-1 都是对的，而且**领先幅度很大**（4.9 vs 1.9）——关键词检索在"查询词和文档用词一致"时非常锐利。

> **必须诚实标注的局限**：上面这个 BM25 是**我用"单字切分"实现的简版**（把 `Python的并发编程` 切成 `['Python','的','并','发','编','程']`），只为演示机制。生产环境必须用真正的分词器（`jieba` 等），否则"并发"会被拆成"并"和"发"两个单字，语义完全丢失。**本节的数字用于理解机制，不要直接用于生产。**
>
> 这个简版还有个直接可见的后果：查询 `装饰器怎么用` 的第 2 名是"生成器"（BM25=1.7666）——它和"装饰器"共享 `"器"` 字（`IDF("器") = 1.0296`）。**纯字面匹配把"器"字当成了相关性证据**，这是字符级匹配的典型误判。

### 5.4 RRF 融合：真实排名对照

有了两路召回，需要把它们合并。**RRF（Reciprocal Rank Fusion）** 是最简单可靠的融合方法：

```
RRF(d) = Σ     ──────────
      r∈路     k + rank_r(d)
```

它**只用排名，不用分数**——这恰好绕开了第 3 节那个"分数跨查询不可比"的麻烦。`k` 一般取 60，作用是压低"排名第 1"的绝对优势，让多路的一致性更重要。

实测（`k=60`）：

**查询 `Python的并发编程`** —— 两路高度一致

| 文档 | 向量排名 | BM25 排名 | RRF |
|---|---|---|---|
| asyncio | **1** | **1** | **0.032787** |
| GIL | 2 | 2 | 0.032258 |
| 多线程 IO | 3 | 3 | 0.031746 |
| 生成器 | 4 | 6 | 0.030777 |
| multiprocessing | 6 | 4 | 0.030777 |
| 装饰器 | 5 | 5 | 0.030769 |

手算核对第一行：

```
RRF(asyncio) = 1/(60+1) + 1/(60+1) = 2 × 0.0163934 = 0.032787  ✓
```

**查询 `装饰器怎么用`** —— 两路出现分歧

| 文档 | 向量排名 | BM25 排名 | RRF | RRF 后 |
|---|---|---|---|---|
| 装饰器 | 1 | 1 | 0.032787 | 1 |
| 生成器 | 2 | 2 | 0.032258 | 2 |
| GIL | 4 | 3 | 0.031498 | **3** ↑ |
| multiprocessing | **3** | 6 | 0.031025 | **4** ↓ |
| 多线程 IO | 5 | 4 | 0.031010 | 5 |
| asyncio | 6 | 5 | 0.030536 | 6 |

**这里能看到融合真正的价值**：向量检索把 `multiprocessing` 排到第 3，但 BM25 把它排到第 6（字面对不上）。**RRF 把它降到了第 4** —— 单一信号的错误被另一路纠正了。同时 `GIL` 从第 4 升到第 3。

> **一个诚实的观察**：两路完全一致时（第一个查询），**RRF 什么也没改变**。混合检索不是"永远更好"，它只在**两路的分歧恰好能互相纠正**时才有收益。所以它必须配合评估（第 7 节）来验证，不能想当然。

### 5.5 什么时候该上混合检索

```
需要精确匹配专有名词/ID/错误码？  → 上 BM25 混合
文档里有大量同义改写/口语化提问？  → 向量是主力，BM25 做补充
数据量小（几百条以内）、查询简单？ → 纯向量就够，别过度工程
```

## 6. Retriever：把检索器变成链上的一个"零件"

`4_retrieval.py` 第 4 节做的事，是把向量库包装成一个统一接口：

```python
retriever = db.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 3, "fetch_k": 6},
)
results = retriever.invoke("Python并发")
```

**为什么要多这一层？** 因为第 5 篇要用 LCEL 把检索器**串进管道**：

```python
chain = {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | llm
```

管道里的每个零件都得有统一的调用方式。`as_retriever()` 就是把"向量库"这个具体对象，抽象成"**输入一个字符串，输出一组 `Document`**"的标准零件。

**关键参数是 `search_type`**，它决定用哪种排序策略——本文前面讲的四种检索方式，全都在这里切换：

| `search_type` | 对应本文 | `search_kwargs` |
|---|---|---|
| `"similarity"`（默认） | 第 2 节 | `{"k": 3}` |
| `"mmr"` | 第 4 节 | `{"k": 3, "fetch_k": 6, "lambda_mult": 0.5}` |
| `"similarity_score_threshold"` | 第 3 节 | `{"score_threshold": 1.0}` |

> 注意第三个：`similarity_score_threshold` 用的仍然是**距离阈值**（越小越好），所以第 3 节讲的"绝对阈值不可靠"在这里同样成立。

## 7. 检索质量怎么评估

第 3、4、5 节反复出现同一句话：*"这个优化到底有没有用？"* 没有指标就没法回答。RAG 的评估必须**把检索和生成分开**（第 1 篇的教训：Top-1 排错了，最终答案却对了——只看最终答案会漏掉问题）。

### 检索侧的指标

| 指标 | 公式 | 回答什么问题 |
|---|---|---|
| **命中率 Hit Rate@k** | 前 k 条里有正确答案的查询数 / 总查询数 | 有没有找回来（召回） |
| **MRR** | `(1/|Q|) · Σ 1/rank_i` | 正确答案排得多靠前（排序） |
| **Recall@k** | 相关文档被召回的比例 | 漏了多少 |
| **Precision@k** | 前 k 条里相关的比例 | 混了多少噪音 |

**MRR 用本文的真实数据算一遍：**

```
查询 "Python多线程有什么限制？"  → 正确文档 GIL 排在 第 1 位  → RR = 1/1 = 1.000
查询 "Python的并发编程" (MMR)     → GIL 排在 第 2 位（MMR 顺序）→ RR = 1/2 = 0.500
                                    GIL 排在 第 3 位（实际返回）→ RR = 1/3 = 0.333
```

**同一组检索结果，因为 4.5 节那个"返回顺序是距离顺序"的细节，MRR 会算出 0.500 或 0.333 两个不同的值。** 这就是为什么评估时**必须固定并明确记录**用的是哪套顺序。

### 生成侧的指标

| 指标 | 看什么 |
|---|---|
| 忠实度 Faithfulness | 回答是否**只**依据了检索内容（有没有编） |
| 答案相关性 | 回答有没有答到问题上 |
| 上下文相关性 | 检索进来的内容是否被用上了 |

工具：**RAGAS**（自动算上面几个指标）、**LangSmith**（LangChain 生态的追踪与评估）。但**人工抽检永远是最可靠的一环**——尤其在项目早期，人工看 20 条比跑一堆自动指标更快发现问题。
